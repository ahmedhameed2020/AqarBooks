# AqarBooks Mobile — خطة اختبار الجهاز الحقيقي (Egypt V1)

الهدف: التحقق على hardware حقيقي من أن التطبيق المنفَّذ (commits `58cebf4` + `15ad6db`) يطابق الـBlueprint وعقود الـbackend قبل قرار إصدار V1.
المرجعان الملزمان: [UX_BLUEPRINT_EGYPT_V1.md](UX_BLUEPRINT_EGYPT_V1.md) و[GATE_CAMERA_SCANNER.md](GATE_CAMERA_SCANNER.md).

## 1. الأجهزة والبيئة

| بند | التفصيل |
|---|---|
| Android (أولوية 1) | جهاز حقيقي Android 10+ بكاميرا خلفية. يُفضَّل جهازان: متوسط (الاستخدام الواقعي للمحصّل/الفني) + ضعيف/قديم إن توفر. |
| iOS (أولوية 2) | يتطلب macOS + Xcode — قسم 8 أدناه. لم يُبنَ لـiOS إطلاقًا حتى الآن. |
| البناء | من `mobile/`: `flutter run --release --dart-define=SUPABASE_URL=… --dart-define=SUPABASE_ANON_KEY=…` (مفتاح publishable/anon فقط — لا service key أبدًا). |
| البيئة | **منظمة اختبار معزولة** (بيانات وهمية بالكامل). لا تُجرَّب flows التحصيل/البوابة على بيانات عملاء حقيقيين. |
| أثناء الاختبار | راقب `access_events` و`payments` و`work_orders` من لوحة الويب/SQL جنبًا إلى جنب — نصف الحالات تتحقق من أثر السيرفر لا من الشاشة فقط. |

## 2. تجهيز بيانات الاختبار (مرة واحدة، من لوحة الويب)

**منظمة:** "AqarBooks QA" → عقار/كمبوند → عمارة → 3 وحدات (A-12, A-13, B-07).

**مستخدمون (7) — الدور هو مفاتيح الصلاحيات، لا الاسم:**

| مستخدم | الإعداد |
|---|---|
| `qa.owner` | member بملكية نشطة لوحدتين (A-12, A-13) + 3 مستحقات على A-12 (واحد `due_date` ماضٍ) + دفعتان سابقتان + طلب صيانة مفتوح |
| `qa.tenant` | member بعقد إيجار نشط فقط (**بلا** `unit_ownerships`) — لاختبار الإخفاء |
| `qa.manager` | دور `PROPERTY_MANAGER` |
| `qa.collector` | دور `COLLECTOR` (بدون `cashier.sessions.open`) |
| `qa.cashier` | دور `CASHIER` + cashbox باسم "خزينة QA" |
| `qa.tech` | دور مخصص **Technician-QA**: `operations.work_orders.view` + `.complete` فقط (الجولة الثانية: أضف `.manage`) |
| `qa.gate` | دور مخصص **Gate-QA**: `operations.gates.scan` + `operations.access_events.view` + `operations.visitors.view` |

**تشغيلي:** بوابة "البوابة الرئيسية" (BOTH) + إصدار gate device enrollment (كود + UUID) لحظة الاختبار (صلاحيته 15 دقيقة) · طلب صيانة TRIAGED + أمر شغل ASSIGNED لـ`qa.tech` بـ`sla_due_at` اليوم · تفعيل فوري test mode للمنظمة إن كان متاحًا (وإلا فحالة «غير مفعّل» هي المُختبَرة) · استثناء بوابة معلق أنشأه `qa.gate`.

## 3. الساكن/المالك (`qa.owner`) — R

| # | الخطوات | المتوقع |
|---|---|---|
| R1 | تسجيل الدخول بالعربية ثم قتل التطبيق وإعادة فتحه | جلسة محفوظة، اللغة محفوظة، RTL سليم، "AqarBooks" باللاتينية في الشاشة |
| R2 | الرئيسية | رصيد A-12 يطابق `members_with_financials`، شارة «متأخر» تظهر لأن `due_date` ماضٍ (وليس اعتمادًا على status=OVERDUE)، switch بين A-12/A-13 يعمل |
| R3 | المدفوعات → «عليّ» | الإجمالي = مجموع المتبقي المحسوب من allocations؛ «دفعت» تعرض الدفعتين الحقيقيتين (**regression لخطأ `member_id` القديم — يجب ألا تكون القائمة فارغة**) |
| R4 | استحقاق → «ادفع عبر فوري» (فوري مفعّل) | شاشة كود مرجعي داخلية (ليس متصفحًا خارجيًا) عبر `create_online_payment_checkout_transaction`؛ نسخ ومشاركة واتساب يعملان؛ بعد السداد (أو محاكاته) تظهر الدفعة بعد سحب للتحديث |
| R5 | نفس الخطوة وفوري غير مفعّل | لا يظهر زر دفع إلكتروني إطلاقًا؛ تظهر إرشادات «السداد عند المحصّل أو مكتب الإدارة» |
| R6 | طلب صيانة جديد: وحدة + تصنيف + وصف + **صورة من كاميرا الجهاز** | رفع موقّع ينجح (begin/finalize)، الطلب يظهر برقم، الإلغاء متاح قبل بدء التنفيذ ويختفي بعده |
| R7 | دعوة زائر → QR → إغلاق التطبيق وفتحه → عرض التصريح | QR محفوظ محليًا ويُعرض ثانية من الجهاز؛ تحذير «احفظ الآن» ظاهر؛ مشاركة واتساب تعمل؛ الإلغاء يطلب تأكيدًا |
| R8 | الدخول بـ`qa.tenant` | أقسام الصيانة/الزوار/المركبات **مخفية** (لا تظهر وتفشل)؛ المستحقات حسب `billing_recipient` |
| R9 | أفرغ البيانات (وحدة بلا مستحقات/زوار) | Empty states مخصصة («ذمتك خالصة ✓»…) وليست «لا توجد بيانات» |

## 4. مدير التشغيل (`qa.manager`) — M

| # | الخطوات | المتوقع |
|---|---|---|
| M1 | الرئيسية «يحتاج انتباهك» | يظهر: المتأخر (محسوب بالتاريخ)، أمر الشغل كاسر الـSLA، الاستثناء المعلق؛ كل بند ينقر إلى شاشة تصرف |
| M2 | شريط الأرقام الأربعة | «تحصيلات اليوم» POSTED فقط بدون REVERSED؛ «الزوار الآن» من `list_gate_current_visitors` (ليس صفرًا ثابتًا)؛ الأربعة قابلة للنقر |
| M3 | الصيانة → بانتظار الإسناد → إسناد لأحد الفنيين + جدولة | `assign_work_order` ينجح؛ يظهر فورًا عند `qa.tech` في «مهامي» |
| M4 | بعد إكمال الفني (T5) → مراجعة | خيارا «إغلاق» و«إعادة فتح إلى TRIAGED» يعملان وينعكسان في الويب |
| M5 | اعتماد استثناء البوابة | الاعتماد يعمل لـ`qa.manager`؛ **ولو كان المدير نفسه منشئ الاستثناء يُرفض** (maker-checker في الـDB) برسالة مهذبة |

## 5. المحصّل/أمين الخزينة — C

| # | المستخدم | الخطوات | المتوقع |
|---|---|---|---|
| C1 | `qa.collector` | فتح التطبيق | تبويبات التحصيل تظهر، **بطاقة الجلسة لا تظهر** (لا `cashier.sessions.open`) |
| C2 | `qa.cashier` | فتح جلسة على «خزينة QA» برصيد افتتاحي | `open_cashier_session` ينجح وتظهر البطاقة |
| C3 | أيهما | بحث بكود الوحدة وبالاسم وبالهاتف | النتائج صحيحة وسريعة |
| C4 | أيهما | تحصيل B-07: تحديد مستحقين → نقدي → تأكيد | إيصال برقم من `next_sequence_value`؛ الدفعة POSTED والـallocations صحيحة في الـDB |
| C5 | أيهما | **اختبار idempotency:** فعّل الطيران لحظة الضغط على «تأكيد»، ثم أعد الاتصال وأعد المحاولة | زر التأكيد يُقفل أثناء الإرسال؛ بعد إعادة المحاولة توجد **دفعة واحدة فقط** في `payments` (نفس `idempotency_key`) |
| C6 | أيهما | شاشة طرق الدفع | نقدي/تحويل بنكي/أخرى فقط — **لا خيار شيك** (لا أحد منهما يحمل `banking.cheques.manage`) |
| C7 | `qa.cashier` | إغلاق الجلسة بمبلغ فعلي مختلف عن المتوقع | المتوقع والفرق يُعرضان؛ الحالة «بانتظار اعتماد التسوية» **بدون** زر اعتماد |

## 6. فني الصيانة (`qa.tech`) — T (جولتان)

**جولة 1 — الصلاحيات `.view` + `.complete` فقط:**

| # | الخطوات | المتوقع |
|---|---|---|
| T1 | «اليوم» و«مهامي» | المهام المسندة له فقط، بكود الوحدة الحقيقي (لا UUID)، مرتبة: متأخر SLA ← عاجل ← الأقدم |
| T2 | فتح أمر ASSIGNED | **لا يظهر زر «بدء»** (يتطلب `.manage`)؛ تظهر الإرشادات بدل زر ميت |

**جولة 2 — بعد إضافة `.manage`:**

| # | الخطوات | المتوقع |
|---|---|---|
| T3 | بدء المهمة | `start_work_order` ينجح والحالة IN_PROGRESS في الويب |
| T4 | تعليق مؤقت | السبب **إلزامي** قبل الإرسال؛ يظهر في timeline |
| T5 | إكمال | الزر معطل حتى كتابة ملخص الإنجاز + صورة AFTER؛ بعدها `complete_work_order` ينجح |
| T6 | طوال الجولتين | **لا يوجد زر إلغاء** على IN_PROGRESS/WAITING إطلاقًا |

## 7. البوابة (`qa.gate`) — G

نفّذ أولًا **كامل checklist الجهاز** في [GATE_CAMERA_SCANNER.md](GATE_CAMERA_SCANNER.md) (11 بندًا: الإذن، الرفض والعودة من الإعدادات، الفلاش، الطيران وidempotent replay، revoke…). ثم أضف:

| # | الخطوات | المتوقع |
|---|---|---|
| G1 | شاشة التفعيل بحقلين | كود بصيغة خاطئة أو UUID ناقص → رسالة إدخال واضحة بلا استدعاء سيرفر؛ كود منتهي (>15 دقيقة) → رسالة آمنة |
| G2 | تفعيل صحيح | `redeem_gate_device_enrollment` ينجح؛ اسم البوابة والاتجاه يظهران تلقائيًا (لا اختيار يدوي)؛ الـcredential في التخزين الآمن |
| G3 | مسح تصريح `qa.owner` الصالح (دخول) | أخضر «مسموح بالدخول» بالاسم/الوحدة/الصلاحية؛ صف ALLOW جديد في `access_events`؛ الزائر يظهر في «الموجودون الآن» وفي عداد المدير M2 |
| G4 | إعادة مسح نفس التصريح SINGLE_USE | أحمر بسبب عربي («مستخدم من قبل») — reason code لا يظهر خامًا |
| G5 | مسح تصريح ملغي وآخر منتهي | أحمر بأسباب عربية مميزة لكل حالة |
| G6 | خروج زائر لم يدخل | كهرماني «يحتاج انتباه» بإجراء واحد واضح |
| G7 | تسجيل استثناء يدوي (walk-in) | يُنشأ REQUEST؛ يظهر عند المدير للاعتماد؛ `qa.gate` **لا يرى** زر اعتماد |

## 10. iOS (يتطلب macOS + Xcode) — I

1. `flutter build ios` بعد `pod install` (الـPodfile يتولد أول مرة؛ هدف iOS 15).
2. إعادة الحالات الحرجة: R1، R4، R6 (كاميرا الصور)، R7، كامل قسم G (إذن الكاميرا بنص `NSCameraUsageDescription`).
3. **اختبار أمان خاص بـiOS:** انسخ backup الجهاز إلى جهاز آخر واستعده → يجب **ألا** يُستعاد credential البوابة (`first_unlock_this_device`) ويطلب التطبيق تفعيلًا جديدًا.

## 11. معايير إصدار V1 (Release Gate)

**Blockers (كلها إلزامية):** R3 (سجل المدفوعات يعمل) · C5 (لا ازدواج دفعات) · G2–G5 (التفعيل والمسح والقرارات) · X2/X4 (لا raw errors ولا سقوط صامت) · عدم وجود crash في أي حالة أعلاه.
**High (تؤجَّل بقرار صريح فقط):** R4/R5 (فوري بالحالتين) · M5/G7 (maker-checker) · T2/T6 (مطابقة الصلاحيات والانتقالات) · P2.
**iOS:** إن لم يتوفر macOS الآن، يصدر V1 **أندرويد فقط** ويُسجَّل قسم 10 كشرط لإصدار iOS.
