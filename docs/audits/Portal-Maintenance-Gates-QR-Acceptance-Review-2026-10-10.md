# Customer portal, maintenance, visitor passes, gates and QR — local acceptance review

Date: 2026-10-10 · Branch `fix/phase1-financial-report-authz` · **Local only** (clean Supabase stack `aqarbooks_clean`, production build served on :3100). Nothing deployed, committed or pushed; production never contacted. The review itself changed only tests and helpers; the follow-up round of 2026-10-11 (§9) added three forward migrations that fix G1 and G2 and hardened the test target. Nothing committed, pushed or deployed.

## 0. Verdict in five lines
1. **The core journey works and is proven end to end through the real screens:** owner signs in → sees only their unit and statement → files a maintenance request → staff triage it → owner follows the status → owner creates a visitor pass → a *guard* scans it from an enrolled device → entry/exit are recorded (18 browser tests, §2–§3).
2. **Isolation holds** between owners of the same organization, between organizations (even with the same unit code), and between owner / staff / anonymous surfaces — on pages *and* in the API, with the database unchanged after every refusal.
3. **Pass rules behave as the ledger contract says** for single-use, multi-use, revoked, expired, not-yet-valid and forged QR codes, and the raw QR secret is never stored.
4. **Two real defects and several gaps were found** (§5). The most important: *amenity-booking decisions break* on a database built from the migrations (a migration regression that also exists in the development database), and *a foreign-organization pass raises a raw database error instead of a recorded denial*.
5. **An incident of mine:** my first runs of existing test files wrote test data into the **development** database (§1.3). It is disclosed, was stopped, and nothing was cleaned.

## 1. Method and legend
### 1.1 How it was done
* Real browser (Playwright, production build, egress-blocking guard) and the real RPCs under each caller's own session. The service key only seeded users/rows and read the six-digit login code (the local stack has no mailbox); every action under review is a product screen or RPC.
* Fixture (`tests/e2e/helpers/portal-fixture.ts`): organization A with owner 1 (unit R-101: charges 3,000 + 1,500, payment 1,000), owner 2 (unit R-202: 7,777), a manager and a guard; organization B with an owner whose unit **also** has code R-101 and a charge of 9,999. Distinct amounts make any leak visible.
* Evidence: `docs/audits/portal-review-evidence/` — run logs, `journey-observations.json`, `visitor-gate-observations.json`, `refusal-observations.json`, `audit-coverage.txt`, screenshots.

### 1.2 Classification used
**W** works and proven · **P** exists but incomplete · **N** does not exist · **T** could not be tested here.

### 1.3 Incident: writes to the development database, and the harness fixes
Sixteen existing integration test files resolve their target with `supabase status` run from the repository (which points at the **development** stack) and/or hard-code the development container name. My first baseline run of them therefore wrote their fixtures into the development database, and a second run (after a partial fix) wrote a second batch. Development organizations went 428 → 442 → 456 across the two later runs (plus the first batch of about 15), i.e. roughly 40+ disposable test organizations, their users, gate devices and events. **Nothing was deleted** (you asked that development data be preserved); they are all named like `Gate RLS A`, `Visitor RLS B`, `Maintenance PR3 A`, `Evidence Org`, `Renewal …`, `Unit Experience A`. I stopped, found the cause, and fixed the *harness*: `run-vitest-local.mjs` and `e2e.mjs` now export `SUPABASE_WORKDIR` (the Supabase CLI honours it), and the 16 files' container name is overridable (`LOCAL_DB_CONTAINER`, default unchanged). After that the development count stayed at 456 through every later run (checked before and after each).
**Second incident (mine, caught and undone):** while building this review's bundle I passed an empty string as the staging folder, which the script treated as the current folder. It wrote `files/`, `MANIFEST.md`, `NOT-INCLUDED.txt`, `SHA256SUMS.txt` into the repository root and **overwrote the tracked `README.md`** (and started zipping from the drive root, which produced a 0-byte file). I stopped it, restored `README.md` with `git checkout` (it had no uncommitted changes — it was absent from the modified-files list at the start of the session), deleted the stray files and the empty zip, and hardened the generator: an empty argument now means the default, and staging is refused anywhere except a sub-folder of the system temp directory (both the repository root and a drive root were tried and refused). `git status` shows no stray files and no `README.md` change.

Consequence for the evidence: the *first* run's results were against the development database and are discarded; the numbers below are from the clean stack.

### 9.1 Addendum (2026-10-11, second pass)
* **Client URL binding.** Every `createClient(url)` in vitest now goes through `tests/setup/guarded-create-client.ts`: before the original constructor is called, the URL must equal the target `assertIsolatedStack` verified (same loopback host class, same API port); the development port (54321 and the repository's own configured port) is refused even if listed in `LOCAL_SUPABASE_API_PORTS` (the list itself no longer admits 54321); port 1 stays the unit-run dummy. * **Runbook** line allowing manual pointing at `54321` replaced by the refusal policy.
* **Hardware outbox failure: cause measured, file moved to its own stack.** `claim_gate_hardware_commands` is one global queue (`order by next_attempt_at, id limit p`, no organization filter), so the file cannot share a database with other suites. Measured: the test "shared queue" (rolled-back transaction) seeds 50 older commands; a plain `claim(50)` returns those 50 and **not** the newer command, which reproduces the empty result of the combined run. The file therefore now runs only through `node scripts/demo-local/hardware-stack.mjs run tests/gate-hardware-outbox-migration.test.ts`, a stack dedicated to it (project `aqarbooks_hw`, API 55431, DB 55432, same migrations: ledger 72/72, no drift; `up|verify|run|down`). The file's claims are the original, unmodified calls; the production worker contract is unchanged. Its first step refuses to run (before creating or claiming anything) when any claimable command of another run exists in the database; started on the shared stack it refuses with 33 foreign commands and the queue fingerprint (hash and 135 rows) is identical before and after. After each run it dead-letters only its own leftovers, so repeated runs on the dedicated stack stay clean (three consecutive runs passed). Passing alone earlier was supporting evidence only; the measurement and the dedicated-stack runs are the proof.
