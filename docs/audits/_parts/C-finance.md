## 0. Cross-cutting model (matters for the customer scenario)

- Permission chain: permissions.key -> role_permissions -> user_role_assignments. has_permission(user, org, key) (baseline L4563) is ORGANIZATION-WIDE and ignores user_role_assignments.property_id. has_financial_permission(org, key, resort_id) (L4485) honours property scope, but is used only by record_payment, record_expense and void_payment. Every other finance RPC (journals, supplier bills/payments, cheques, bank reconciliation, cashier, budgets, assets) is org-wide.
- UI to assign a role to a user for ONE resort: NOT FOUND (lib/actions/users.ts writes user_role_assignments without property_id). Property-scoped permission is DB-capable but not operable from the admin UI. Confidence medium-high.
- Custom roles: lib/actions/roles.ts (tenant.roles.manage) plus 12 role templates (TENANT_OWNER, TENANT_ADMIN, GENERAL_MANAGER, FINANCE_MANAGER, ACCOUNTANT, CASHIER, COLLECTOR, AUDITOR, PROPERTY_MANAGER, STOREKEEPER, PURCHASING_MANAGER, VIEWER; supabase/baseline/baseline_04_reference_data.sql L228). Custom composition of keys is possible.
- Financial entity: the tenant is `organizations` (one legal entity: currency, status, tax identity). Sub-units are `properties` (exposed as view `resorts`) = the "branch/site" concept. Journals, dues, payments, expenses, cost_centers carry property_id. Bank accounts and cashboxes are org-level GL-linked records. There is NO separate legal-entity or branch table and no consolidation.
- Entitlements: plan_entitlements rows (STARTER/PROFESSIONAL/ENTERPRISE: max_resorts, max_users 5/25/..., max_units, finance_module, cashier_module, banking_module, fixed_assets_module, inventory_module, purchasing_module, advanced_reports, ...; baseline_04 L145+) are only readable via get_entitlement() (baseline L4109). A grep of lib/, app/, components/, middleware and later migrations finds NO caller. Per-user-count, per-module and per-resort limits are DATA ONLY (BACKEND ONLY, not enforced). tenant_feature_flags has no reader either. Priority P1.
- Audit trail: platform_audit_logs written by most RPCs; hash-chained financial_audit_logs with verify_financial_audit_chain (fixed in final_hardening). Report /finance/reports/audit-trail reads platform_audit_logs.
- Maker-checker: journals have DRAFT -> UNDER_REVIEW -> POSTED -> REVERSED with separate keys (entries.create/review/post/reverse) but no DB rule that poster differs from creator. Expenses, supplier bills and payments post immediately (no approval step).

## 6. Customer scenario assessment (village accountant vs Cairo office, ONE entity)

1. One organization with one or more resorts is supported. "Branch" = properties/resorts. Bank accounts and cashboxes are org-level, not tied to a site. No separate branch entity or consolidation.
2. Village accountant "collections + expenses only" is achievable only through a custom role (tenant.roles.manage) containing receivables.payments.create, finance.payments.read/create, finance.dues.read, finance.entries.create (required by record_expense), finance.expenses.read, plus cashier.* if used. Side effect: finance.entries.create also lets that user create draft journals and post supplier invoices and supplier payments (both RPCs require it). They cannot post or reverse journals without entries.post/reverse. Collections and expenses are resort-scoped in the DB, but the admin UI cannot assign a resort-scoped role.
3. Cairo "bank deposits + general bills": deposits use receivables.payments.create and must be matched to dues; there is no unidentified or advance deposit. Bills use finance.entries.create. Separating deposits from bills is expressible by key, but deposit-without-due is not functional.
4. Per-user-count entitlement: max_users exists as data (5/25/...) but is NOT enforced; module flags are not enforced either.
5. Accounting-code/report design help: CoA is editable and clonable from a single resort template; no import/export, no association template, cost centres unusable, no report builder or custom statement layouts.
