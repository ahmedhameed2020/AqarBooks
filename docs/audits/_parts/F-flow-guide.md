# F - Connected accounting journey: UI drive guide + expected effects

Scope: read-only study (source + local clean DB function bodies, 2026-10-10). Journey = opening balance 10,000 (before report period) -> due 2,000 (in period) -> payments 1,500 and 500 -> full reversal of the 500 -> expected net collected 1,500, remaining 10,500.
Function bodies below were read from the LIVE local DB (`pg_get_functiondef`), not only from migrations (the migrations dir is a squashed baseline + deltas).

## 0. Verdict first (things that change how the journey must be written)

1. **Every GL-derived report will be wrong after the reversal (probable defect, high confidence from source).** `void_payment` sets the ORIGINAL receipt journal entry to `status='REVERSED'` AND posts a mirror reversal entry `status='POSTED'`. `get_trial_balance`, `get_account_ledger`, `get_cash_flow_statement`, `get_cash_position` and `get_bank_reconciliation_summary` all filter `je.status = 'POSTED'` only. So the original receipt vanishes and the mirror stays: the net GL effect of a void is the NEGATIVE of the receipt instead of zero. With the journey: cash/bank TB = 1,500 - 500 = **1,000 (expected 1,500)**, AR 1130 = **Dr 11,000 (expected 10,500)**. TB/BS still "balance" (both legs wrong), so the balance check will not flag it. Sub-ledger screens (dues list, owner statement, payments list, aging) are computed from `payments.status` and show the CORRECT 1,500 / 10,500. The same pattern exists in `reverse_journal_entry`. `tests/final-hardening.integration.test.ts` L133-224 never re-reads the TB after the void, so it is untested. Verify empirically with one TB read after the void; assert BOTH the intended numbers and the predicted ones so the test documents the defect.
2. **Single-due allocation only in the UI.** The record-payment dialog allocates the whole payment to ONE due. `RecordPaymentForm` (multi-allocation) exists but is imported nowhere. One payment cannot be split across the opening due and the new due. Two payments can hit the same due (partial pays are fine) - the DB checks remaining.
3. **A prior-year opening date does not fail - it silently produces no journal entry** unless an OPEN fiscal period covers that date (`post_due_to_ledger` returns NULL when no OPEN period contains `issue_date`; the due is still created, status ISSUED, `journal_entry_id` NULL, success toast shown). Recognise later via periods page after creating/opening the prior period.
4. **Role gaps for an ACCOUNTANT user** (live `role_template_permissions`): ACCOUNTANT has finance.dues.read/issue, receivables.payments.create, finance.payments.create/read, finance.reports.read, finance.bank_reconciliation.manage/read, property.reports.read - but NOT `finance.payments.void` (void), `finance.periods.manage` (fiscal year/period open), `finance.accounts.manage` (create due type, banks, bank accounts, COA clone), `finance.entries.post` (recognise dues). Only FINANCE_MANAGER and TENANT_OWNER have those four. For a one-user journey use FINANCE_MANAGER (superset of everything needed) or seed setup by service role and sign in as ACCOUNTANT, switching to a FINANCE_MANAGER only for void. Note `has_financial_permission` also has an "organization creator bypass" (`organizations.created_by = auth.uid()`), irrelevant for fixtures where created_by is null.
5. **Payment method BANK_TRANSFER is not selectable.** UI offers CASH / CHEQUE / ONLINE only (`payments-dialog.tsx` L47-51) and `recordPaymentAction` zod enum is `["CASH","CHEQUE","ONLINE"]` (`lib/actions/receivables.ts` L135) although DB `payments_method_check` allows BANK_TRANSFER. For a bank collection pick method CHEQUE (or ONLINE) with deposit account = the bank's GL account.
6. **UI defaults are traps** (all use `list[0]`, no ordering guarantee or wrong ordering): Issue-due receivable account defaults to the first ASSET leaf by code = **1110 Cash/الصندوق**, not 1130; due type default may be the auto-created "Opening Balance" type; payment dialog default member = first by name, default due = first open due, default period = first OPEN period (unordered), deposit account list = ALL ASSET leaves (incl. receivable 1130). Always select every combobox explicitly.
7. The "reference / cheque #" input on the payment dialog is dropped (not in the action schema) - nothing is stored; `receipt_no` is never set (only numeric `receipt_number`).
8. Reversal entry is dated `current_date` (real today), and needs an OPEN period containing today (`NO_OPEN_REVERSAL_PERIOD` otherwise). Keep the current month OPEN even if the journey uses other months.

- Settings: `organization_finance_settings` (online-payment clearing, security deposit, commission accounts) is NOT read by dues/payments/opening-balance flows. ## 2. Member opening balance

- **Route**: `/ar|en/members/{memberId}`. Button (outline, amber scale icon) text "Opening balance" / "رصيد افتتاحي" (only rendered when `finance.dues.issue`). Dialog (Base UI `Dialog`, not native): title "Record client opening balance" / "تسجيل رصيد افتتاحي للعميل".
- **Controls**: Unit = Base UI Select combobox labelled "Unit"/"الوحدة" (options `CODE • building`; default first unit); amount `#ob-amount` (number, min 0.01, step 0.01); as-of date `#ob-date` (type=date, default AND `max` = today UTC); optional receivable account select "Receivable account"/"حساب الذمم المدينة" (shown only if ASSET leaves exist; left empty = server default); memo `#ob-description` (max 500). Submit "Record balance" / "تسجيل الرصيد" (disabled until unit+amount>0+date). Success toast "Opening balance recorded"/"تم تسجيل الرصيد الافتتاحي"; error shown in `role="alert"` inside the dialog.
- **Units offered**: only the member's CURRENT `unit_ownerships` (page.tsx L98-118: ownerships with end_date null/future). A tenant-by-lease member gets no unit in the dialog (the empty-state says link first) even though the DB trigger accepts an ACTIVE lease.
- **Action/RPCs**: `recordMemberOpeningBalanceAction` (`lib/actions/member-opening-balance.ts`) -> `recordOpeningBalance` (`lib/finance/opening-balance.ts`): RPC 1 `ensure_opening_balance_due_type(p_organization_id)` (own txn) then RPC 2 `record_member_opening_balance(p_organization_id,p_member_id,p_unit_id,p_amount,p_as_of_date,p_receivable_account_id,p_description)`.
- **Constraints** (live fn): auth required; not demo org; amount > 0; date required and **`p_as_of_date <= current_date`** (no lower bound - may be before the report period, prior month/year); unit exists, not archived, in org; `has_financial_permission('finance.dues.issue', unit.property_id)`; member exists/not archived; link check (ownership with end_date null/>= today, or ACTIVE lease) PLUS a table trigger `dues_opening_balance_current_unit_link` that additionally needs `ownership.start_date <= today` / lease `starts_on <= today < ends_on`; one non-VOID OPENING_BALANCE due per (member, unit) -> `OPENING_BALANCE_ALREADY_RECORDED`; receivable account (if given) must be active leaf ASSET in org. Default receivable = the receivable account used by the most existing dues of the org (any ASSET leaf!), else account code **1130**, else `RECEIVABLE_ACCOUNT_REQUIRED`. Under tax enforcement it additionally needs an APPROVED non-taxable revenue-nature mapping (`OPENING_BALANCE_TAX_MAPPING_REQUIRED`) - not applicable (enforcement off).
- **Accounting effect**: `ensure_...` first time creates equity leaf account **code 3900** (first free in 3900-3999) "أرصدة افتتاحية — ذمم العملاء" / "Opening Balances - Receivables", EQUITY/CREDIT, parent 3000, plus due type "رصيد افتتاحي"/"Opening Balance" whose `default_revenue_account_id` = that equity account; platform audit `due_type.opening_balance_created`. The due is inserted `status='ISSUED'`, `issue_date = due_date = as-of`, `source_type='OPENING_BALANCE'`, `source_id = member_id`. AFTER INSERT trigger `trg_dues_post_to_ledger` -> `post_due_to_ledger`: finds the OPEN fiscal period containing `issue_date`; **if none -> returns NULL, no JE, no error**. If found: JE `entry_date = as-of`, `source_type='JOURNAL_VOUCHER'` (note: not a dedicated type), status POSTED, `idempotency_key = 'due:<due_id>'`, description = memo or `رصيد افتتاحي — <member name>`, lines **Dr receivable (1130) 10,000 / Cr 3900 equity 10,000**; `dues.journal_entry_id` set; platform audit `journal_entry.created` + `journal_entry.posted` (entry_number from `document_sequences` type `journal_entry`); `chart_of_accounts.is_used=true`. Hash-chained `financial_audit_logs` row action `OPENING_BALANCE_RECORDED`, entity_type DUE, entity_id = due id, metadata {member_id,unit_id,amount,as_of_date,receivable_account_id,due_type_id}. No revenue, no VAT. Due shows in dues list with type "Opening Balance"/"رصيد افتتاحي" and due_date = as-of (aging counts from then: > 90 days bucket "90+ days"/"أكثر من 90 يوم" if old enough).
- Existing proof: `tests/member-opening-balance.integration.test.ts` (9 tests).

- **Route**: `/ar|en/finance/dues` (read guard `finance.dues.read`; button needs `finance.dues.issue`). Page uses the FIRST resort (`resorts` order created_at asc); the chosen unit MUST belong to that resort (`issue_dues` raises `الوحدة المحددة (%) غير موجودة أو لا تنتمي لهذه المنظمة والمنتجع`).

Order: Unit select (label "Unit"/"الوحدة المستحقة"), Due Type ("Due Type"/"نوع المستحق / البند"), Receivable Asset Account ("حساب الذمم المدينة (أصول)") - **must pick 1130, default is 1110**, Fiscal Period ("Fiscal Period"/"الفترة المالية المفتوحة" - OPEN periods only; value is validated non-empty but NOT sent to the RPC; the JE period is derived from issue_date), Due Amount (`input[type=number]`, min 0.01), Issue Date (first `input[type=date]`, default today UTC), Due Date (second date input, default today), Description input (placeholder "e.g. Q2 maintenance fee"). Toast "Due Issued Successfully"/"تم إصدار المستحق بنجاح"; server errors rendered as raw `error.message` in `role="alert"`.
- **Action/RPC**: `issueDueAction` (`lib/actions/receivables.ts` L54) -> `issue_dues(p_organization_id,p_resort_id,p_unit_ids=[unit],p_due_type_id,p_receivable_account_id,p_amount,p_amount_by_unit_type=null,p_issue_date,p_due_date,p_description)`. Needs `finance.dues.issue` (resort-scoped). Constraints: `dues.amount > 0`, **`due_date >= issue_date`** (table check `dues_check`), status inserted ISSUED (no DRAFT path in UI); duplicate guard silently SKIPS (returns skipped_count, UI still toasts success!) when same unit+type+issue_date+identical description non-VOID exists. Paid = allocations whose payment is POSTED; remaining = max(0, amount - paid); VOID/DRAFT dues are still listed and summed in "Total Issued".

## 4. Record a payment

- **Route**: `/ar|en/finance/payments` (read `finance.payments.read`; button gated by `receivables.payments.create`; void button by `finance.payments.void`). Button "New Receipt" / "تسجيل سند قبض جديد". Dialog "Record Payment Receipt" / "تسجيل سند قبض وتحصيل مالي" (`payments-dialog.tsx`). Also `?unit=<unitId>` preselects nothing meaningful (prop unused for selection).
- **Controls** (no ids/testids; positional): "Target Due Demand *" Base UI Select - options text `"<unitCode> - <ORIGINAL amount> <cur> - (Rem: <remaining> <cur>)"` (Arabic "متبقي:"), only dues with status ISSUED/PARTIALLY_PAID/OVERDUE; **choosing a due auto-fills amount = remaining**; "Client / Member *" select (default first member alphabetical - not tied to the due); "Payment Method *" (Cash/Cheque/Online; Arabic "نقدي (Cash)", "شيك بنكي (Cheque)", "دفع إلكتروني (Online)"); "Deposit Account *" (ASSET leaves "code - name", unordered); "Fiscal Period *" (OPEN periods; must be the period containing the payment date); "Amount Paid *" (number); "Payment Date *" (date, default today UTC); "Reference / Cheque #" (ignored). Submit "Record Receipt" / "حفظ وترحيل سند القبض". Disabled when no open dues (message "No open dues available for payment allocation.").
- **Action/RPC**: `recordPaymentAction` (`lib/actions/receivables.ts` L145) -> `record_payment(...)` (checks `has_financial_permission('receivables.payments.create', resort)`) -> `post_payment_internal`. Allocation = exactly `[{due_id, amount}]` from the dialog (no FIFO, no auto-split; amount must equal sum of allocations, `ALLOCATION_EXCEEDS_REMAINING`, `DUE_RESORT_MISMATCH`, `DUE_VOID`). Remaining recomputed under row lock from allocations of POSTED payments.
- **Idempotency / double-submit**: key = `randomUUID()` generated **inside the server action on each invocation** (`p_idempotency_key`), unique index `idx_payments_idempotency (organization_id,idempotency_key)`. So server-side replay protection works only for a retried identical RPC, NOT for a second user click/new action call. Double-click protection is client-side only: `useTransition` `isPending` disables the submit button. Advisory lock `record_payment_<org>` serialises. A retried form submission after a timeout would create a duplicate receipt.
- **Accounting effect**: JE `entry_date = payment_date`, `fiscal_period_id` = the SELECTED period (must be OPEN and contain the date), `source_type='RECEIPT_VOUCHER'`, `idempotency_key` NULL, POSTED, description "Payment received", lines **Dr deposit account (cash 1110 / bank 1120) = amount; Cr each allocated due's `receivable_account_id` (1130)**. `payments` row: `status='POSTED'`, `receipt_number` = next in `document_sequences('receipt')` per org (1, 2, ... shared across org; `receipt_no` stays NULL), `unallocated_amount=0`, `journal_entry_id`, `created_by`, `method`, `unit_id` (from due), `member_id` (from the member select). `payment_allocations` rows (payment_id, due_id, amount; `reversed_at` NULL). Due status becomes `PAID` if posted-paid >= amount else `PARTIALLY_PAID`. Audit: platform_audit_logs `payment.recorded` (safe_change_summary {amount, receipt_number, cashier_session_id}) + `journal_entry.created`/`journal_entry.posted`. **No `financial_audit_logs` row is written for payment creation** (only dues/opening/void write the chain); the allowed values PAYMENT_CREATED etc. are unused. `trg_notify_payment_confirmed` fires (notification).
- Journey mapping suggestion: Pay#1 1,500 -> opening-balance due (remaining 8,500, PARTIALLY_PAID); Pay#2 500 -> new 2,000 due (remaining 1,500, PARTIALLY_PAID). Receipt numbers #1, #2. JE entry numbers (org sequence `journal_entry`): opening due JE (if posted) -> due JE -> receipt 1 -> receipt 2 -> reversal.
- Payments list (limit 300): columns Receipt #, Client/Member, Method, Payment Date, Amount Paid, Status badge ("Posted"/"✓ مرحل ومعتمد", "Reversed"/"معكوسة"), Actions ("Reverse"/"عكس", "Print"/"طباعة السند"). Filters: status tabs (All/Posted/Reversed = "الكل / مرحل ومعتمد / معكوسة"), method select, search box. Receipt cell renders `#<number>`. KPI "Total Collections" / "إجمالي المقبوضات المحصلة" sums POSTED only; "Total Receipts"/"عدد عمليات التحصيل" counts ALL rows (reversed included).
- Receipt print: "Print"/"طباعة السند" -> `generatePaymentReceiptPdf` builds an HTML Blob, `window.open(url,"_blank","noopener")` and calls `window.print()` in it. In Playwright listen on `context.waitForEvent('page')`; content has "Receipt No:"/"رقم الإيصال:", "Amount Paid"/"المبلغ المدفوع", status "POSTED"/"REVERSED" (REVERSED receipts can still be printed and print "REVERSED"/"معكوسة"). Allocations table inside lists unit, description, due date, allocated amount.

## 5. Reverse (void) a payment fully

- Same page: row button "Reverse"/"عكس" (only POSTED rows, only with `finance.payments.void`). **Uses native dialogs**: first `window.confirm` (en: "This reverses the journal entry for receipt #<n> and reopens its dues. Continue?"; ar: "سيتم عكس القيد المحاسبي لسند القبض #<n> وإعادة فتح الاستحقاقات المرتبطة. هل تريد المتابعة؟") then `window.prompt` ("Enter the required reversal reason:" / "أدخل سبب العكس الإلزامي:"). Playwright: `page.on('dialog', d => d.type()==='confirm' ? d.accept() : d.accept('reason text'))` (empty/whitespace reason aborts silently). Then toast "Payment reversed"/"تم عكس الدفعة" and `window.location.reload()`.
- Action/RPC: `voidPaymentAction` -> `void_payment(p_organization_id,p_payment_id,p_reason,p_ip_address,p_user_agent)`. Checks: reason non-empty (<=1000), `finance.payments.void` (resort scoped), status POSTED (`ALREADY_REVERSED`/`NOT_VOIDABLE`), original JE POSTED, **an OPEN period containing `current_date` must exist (`NO_OPEN_REVERSAL_PERIOD`)**.
- Effects: all of the payment's allocations get `reversed_at/by` set (rows kept); each affected due re-derived: PAID if still fully paid, PARTIALLY_PAID if any posted paid >0, else `OVERDUE` if `due_date < current_date`, else `ISSUED` (in the journey the new 2,000 due had only the reversed 500, so it returns to ISSUED, or OVERDUE if its due_date is already before today); reversal JE: `entry_date = current_date`, period = open period containing today (NOT the original payment's period), `source_type='PAYMENT_VOUCHER'`, idempotency `payment-reversal:<payment_id>`, description "Payment reversal: <receipt_number>", lines = original lines with debit/credit swapped (Cr cash / Dr AR), POSTED with its own `entry_number`; original JE -> `status='REVERSED'`; reversal JE `reversed_entry_id = original`; `payments`: `status='REVERSED'`, `reversed_at/by`, `reversal_reason`, `unallocated_amount=0`, `reversal_journal_entry_id`. Audit: `financial_audit_logs` action `PAYMENT_REVERSED` (entity PAYMENT; metadata reason, original_amount, reversal_journal_entry_id, affected_due_ids, reversed_allocations[...]) + platform `journal_entry.created/posted`. DB triggers `prevent_unreverse_payment(_allocation)` stop un-reversing. Receipt number is not reused.
- Visibility after void: payment still listed (badge "Reversed"/"معكوسة", filter tab works, row has no Reverse button, Print still available); excluded from dues list Paid column, owner statement, aging, member page "totalPaid" (all filter `payments.status='POSTED'`); Dues list status for the due shows the re-derived status. GL: see verdict #1.

## 7. Bank collection + reconciliation

**Recording a bank collection via UI**: payments dialog with Method = Cheque (or Online; BANK_TRANSFER not offered), Deposit Account = the bank's GL account (the one linked in `bank_accounts.gl_account_id`, e.g. "1120 - البنوك / Banks"), Fiscal Period containing date. JE: Dr 1120 / Cr 1130, `RECEIPT_VOUCHER`. Alternative bank flows exist: finance/banks "Record Incoming Cheque" -> "Clear" (`record_incoming_cheque` / `clear_incoming_cheque`, `treasury.ts` L240-345) which post to the bank's GL account too. Cashier page (`payDueFromCashierAction`) is cash-only and requires an OPEN cashier session whose cashbox `gl_account_id` equals the deposit account (and passes member_id null).
- Bank master data: `/{loc}/finance/banks` "Add New Bank"/"إضافة بنك جديد" (fields name AR/EN; `banks` insert) and "Add Organization Bank Account" (bank select, name, number/IBAN, "Linked GL Asset Account" - **default option is `assetAccounts[0]`, check it is 1120**). `bank_accounts` unique (bank_id, account_number). Both need `finance.accounts.manage`.

**Reconciliation** `/{loc}/finance/banks/reconciliation` (read: `finance.bank_reconciliation.read|manage`; the page does its own check - no redirect).
1. "New Statement"/"إنشاء كشف حساب جديد" button -> dialog "New Bank Statement for Reconciliation"/"إنشاء كشف حساب بنكي للمطابقة" (`CreateStatementDialog`; fields via Base UI select + inputs: bank account, Period Start (date), Period End (date), Opening Balance (per Bank), Closing Balance (per Bank), note; submit "Create Statement"/"إنشاء كشف الحساب"). (`CreateStatementForm` in statement-forms.tsx with `#bankAccountId #periodStart #periodEnd #note #openingBalance #closingBalance` is NOT mounted.) Action `createBankStatement` -> direct insert `bank_statements` (status DRAFT). Constraints: `UNIQUE (bank_account_id, period_end)` (23505 -> "A statement already exists ... same end date"), `period_end >= period_start`, status in (DRAFT, RECONCILED). Opening/closing are free numbers (not validated against GL).
2. List row button "Reconcile"/"بدء المطابقة" (or "View Statement"/"عرض تقرير المطابقة" when RECONCILED) -> `/{loc}/finance/banks/reconciliation/{statementId}`.
3. **Import**: textarea `#raw` (name `raw`, dir ltr) "Paste statement rows"/"الصق سطور كشف الحساب", button "Import"/"استيراد". One line per row: `YYYY-MM-DD`, description, amount[, reference]; separators tab or comma (commas inside double quotes OK); amount signed from the account holder's view (+ money in, - money out), thousands separators/currency symbol stripped (`[^\d.\-+]`), 0 rejected; any malformed line rejects the WHOLE paste (`parse_error:<line numbers>`); nothing de-duplicated - importing twice duplicates lines (no unique constraint on lines). Example: `2026-10-05<TAB>Transfer from tenant<TAB>1500<TAB>REF-1`. Table `bank_statement_lines` (amount <> 0; `matched_journal_entry_line_id` UNIQUE -> one GL line can back only one statement line; check `match_coherent`: match id, match_type (AUTO|MANUAL) and matched_at all set or all null).
4. **Auto-match**: "Auto-match"/"مطابقة تلقائية" with `#toleranceDays` (default 5, 0-60) -> `auto_match_bank_statement(p_statement_id,p_date_tolerance_days)`: for each unmatched line, count POSTED journal lines on the bank's GL account where `(debit - credit) = line.amount`, `entry_date` within +-tolerance, and not already matched; exactly 1 -> matched `AUTO`; >1 -> left (ambiguous); 0 -> left. Badge "Auto Matched"/"✓ مطابق تلقائياً".
5. **Manual match**: per unmatched line a native `<select name="journalLineId">` (placeholder "Choose entry…"/"اختر القيد…", option text `#<entry_number> - <entry_date> - <description>`; candidates from `get_bank_match_candidates` tolerance 30 days, same amount rule, max 50, only unmatched) + "Match"/"ربط" button -> direct UPDATE (`match_type MANUAL`). Unmatch: "Unmatch"/"إلغاء المطابقة". Duplicate prevention: UNIQUE on matched_journal_entry_line_id (error "already_matched" message "That journal line already backs another statement line…"). No candidate -> text "No candidate - may need a journal entry". NOTE manual match does not itself verify the GL line is on the bank account (candidates are filtered, the update is not).
6. **Proof table** (`get_bank_reconciliation_summary`): Closing balance per bank (as typed); "+ In books, not in bank (n)" = Σ(debit-credit) of POSTED bank-GL lines with entry_date within [period_start, period_end] that are unmatched; "- In bank, not in books (n)" = Σ unmatched statement lines; "Balance per ledger books" = Σ(debit-credit) of ALL POSTED bank-GL lines with entry_date <= period_end (cumulative from inception); **Difference = (closing + unmatchedGL - unmatchedStmt) - book**. "Perfectly Balanced (Zero Variance)"/"✓ مطابقة تامة ومتوازنة بالكامل" when |diff| < 0.005, else "Unexplained Difference:"/"الفرق غير المفسَّر بين البنك والدفاتر:". The opening balance field is displayed but NOT used in the formula; GL entries dated before period_start are only in `book`, so a bank GL with prior un-reconciled history makes difference non-zero unless closing includes it.
7. **Finalize**: button "Finalize reconciliation"/"اعتماد المطابقة" (disabled while unbalanced; text "Finalizing unlocks once the difference reaches zero."/"الاعتماد متاح فقط عندما يصبح الفرق صفرًا.") -> `finalize_bank_reconciliation` sets `status='RECONCILED'`, `reconciled_at/by`; refuses unbalanced (`RECONCILIATION_NOT_BALANCED`, tolerance = 10^-decimals/2). After finalize the same button reads "Reopen"/"إعادة فتح" -> `reopen_bank_reconciliation` -> DRAFT. While RECONCILED, import/auto-match/match are hidden and RLS (`bank_statement_lines_manage`) blocks line writes. Dashboard counters on the index page: Reconciled / In Progress statements.
- **Scenario guidance**: for a clean reconciliation, put the 1,500 receipt (not the reversed 500) on the bank GL, statement lines `+1500`, closing = 1500 (opening 0), period covering the payment date, `period_end` >= payment date. If the REVERSED receipt were also on the bank account, the GL shows the mirror -500 (dated today) with the original excluded (verdict #1) so book = 1,000 and the proof table cannot balance against a statement that never saw the 500 unless the reversal line is matched by a -500 statement line - i.e. the defect leaks into reconciliation. Cheque-clearing pairs and bank fees need their own JE (none exists in UI except Journals).

## 10. Things that would block the journey as literally written

- Opening 10,000 "before the report period" via UI: works only if as-of <= today; GL effect only if an OPEN period covers it (else no JE; due still collectable - then Cr to AR makes AR negative in GL). Create/open the prior period first (needs finance.periods.manage) or recognise later.
- Payment split across the two dues in one receipt: impossible in UI (two separate receipts needed - consistent with the requested 1,500 / 500 scenario if each targets one due).
- Void by an ACCOUNTANT: impossible (permission) -> use FINANCE_MANAGER/TENANT_OWNER for that step; also requires today's month OPEN.
- Payment method bank transfer: unavailable.
- Receivable default trap on the issue form (1110) and equity/opening type appearing in the due-type list.
- Owner statement requires `property.reports.read` + the member must own the unit through `unit_ownerships`.
