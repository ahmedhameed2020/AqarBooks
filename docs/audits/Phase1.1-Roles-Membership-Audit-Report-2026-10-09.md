## 2. Findings per item

**Item 1 — role replacement through the app.** The server path (`updateRolePermissionsAction`) already checked active membership, `tenant.roles.manage`, role ownership, owner rules and the amplification ceiling in application code, then called the database with the service key, which trusted whatever it was given. That is the gap: the service key was effectively the authorization. The database now checks the requester itself. `tests/role-permissions-authz.integration.test.ts` (24 tests) drives the **real server action** against the local DB for: unauthenticated, no `tenant.roles.manage`, another organization's owner (both naming org A, and naming their own org with org A's role), suspended, invited, non-member, amplification by a non-owner, a non-owner touching `TENANT_OWNER`, clearing owner permissions — every denial leaves the role's grants and the audit trail unchanged — plus positive cases. A second block calls the **function directly** (service key as the caller, each case naming an actor) and shows the database refuses on its own; signed-in and anon clients cannot call it. *Negative control:* replacing the function with a no-check body fails 10 of 24 (all DB-level), while the app-level tests still pass — the two layers are independent.

**Item 2 — `is_org_member` policies.** Before: `status <> 'suspended'`, so **`invited` was treated as a member** (suspended was already excluded — the 9 Oct claim that suspension left access intact was wrong; invited was the real gap). 42 policies and 4 functions depend on it (chart of accounts, fiscal years/periods, journal lines, members, units, properties, banks, cheques, budgets, …; `list_projects`; three gate-device functions). Invitation flow in the code: `inviteUserAction` creates the auth user and an `invited` membership + role; there is no automatic invited→active step — an administrator activates through `updateUserStatusAction`. The invited user's only pre-activation reads are their own membership row (`app/[locale]/onboarding`, `lib/auth/org-context`) and the organization shell; those are preserved and tested. `tests/membership-status-access.integration.test.ts` (17 tests, real sessions): direct reads of 7 tables and 3 views (invited, suspended, outsider = 0 rows; org-B staff sees none of org A); 7 RPCs (`get_trial_balance`, `get_account_ledger`, `get_cash_position`, `get_cash_flow_statement`, `get_unrecognized_dues_summary`, `verify_financial_audit_chain`, `list_projects`) succeed for the active member and return `42501` for invited/suspended/outsider/other-org staff; invitation path (own membership, org shell, no other members' rows); activation through the real `updateUserStatusAction` grants access immediately and suspension removes it; catalog invariants. *Negative control:* with the old `is_org_member`, 5 tests fail (all invited-related).
Behavioural consequence to be aware of: the three gate-device functions and `list_projects` use `is_org_member`, so an *invited* gate operator can no longer enroll/release a device or list projects until activated.

**Item 3 — `check_audit_action`.** Writers found from the current function definitions and every migration: `issue_dues` (`DUE_ISSUED`/`DUE_BATCH_ISSUED`), `generate_recurring_dues` (`RECURRING_DUES_GENERATED/SKIPPED`), `generate_lease_rent_dues` (`LEASE_RENT_DUE_GENERATED`, `OPERATION_REJECTED`; `LEASE_RENT_DUE_SKIPPED` is a baseline value), `create_installment_plan` (`DUE_BATCH_ISSUED`), `record_member_opening_balance` (`OPENING_BALANCE_RECORDED`), `void_payment` (`PAYMENT_REVERSED`); `PAYMENT_CREATED / PAYMENT_IDEMPOTENT_REPLAY / PAYMENT_ALLOCATION_CREATED` are baseline values no current function emits (kept to avoid invalidating historical rows). Proven: `tests/financial-audit-actions.test.ts` (static: every action any migration emits is in the latest allow-list; fails if a later migration shrinks it again), `tests/financial-audit-constraint.integration.test.ts` (7: all 12 accepted, constraint is exactly that set, `BOGUS_ACTION`, wrong case, empty, trailing space, truncated value all rejected with `23514`), and `member-opening-balance.integration.test.ts` (9/9): the user-session RPC creates an `OPENING_BALANCE` due, a POSTED journal Dr receivable / Cr equity with the right amounts and idempotency key, updates unit/member balances, writes exactly one `OPENING_BALANCE_RECORDED` chain row referencing the due, refuses duplicates and bad accounts.
**Dunning delivery — correction to the request's assumption:** delivery does *not* touch `financial_audit_logs` and creates no journal entry; `record_dunning_delivery` updates the notice and writes `platform_audit_logs` (`dunning_notice.delivered`). The failing dunning test was not an audit-constraint failure (see §4). New test: delivery as an authorized user → state `DELIVERED`, channel/reference stored, one audit row by that user, **no journal entry created**, second delivery refused, invalid channel refused with state unchanged.

**Item 5 — blocked-function matrix; corrected counts.** Phase 1's test covered **12 of the 13** helpers (it omitted `compute_input_tax_split`, 6 arguments). The correct counts: Phase 1 withdrew **13 helpers + `replace_role_permissions_atomic` + trigger function `enforce_unit_ownership_total` = 15 functions** (16 `REVOKE` statements, because the 3-argument role-replacement signature was superseded by 4-argument one in 1.1), and re-guarded `get_trial_balance` (so **16 functions changed** overall; the Phase 1 report's "14" was wrong). `tests/revoked-function-matrix.integration.test.ts` (4) derives the list from the migrations' `REVOKE … authenticated` statements, resolves every signature in the live catalog, pins the size (16 statements → 15 live functions), asserts no `PUBLIC/anon/authenticated` EXECUTE and `service_role` kept, that the superseded overload no longer exists, and **calls the 14 RPC-callable functions as a signed-in user and as anon, each refused with `42501`** (argument lists generated from the catalog). The grant-baseline test also gained `is_org_participant`.

## 3. Item 7 — migration sequence on a separate, empty database

Done without touching the dev database: a **new Postgres container** (`aqarbooks_replay_db`, same image `supabase/postgres:17.6.1.165`, port 54399, no volume sharing). The image supplies roles and `auth.users`; the platform-owned `storage` schema is created by the storage service, so it was seeded with a **schema-only dump of the dev stack's `storage` schema** (read-only `pg_dump`; project policies on `storage.objects` removed so the migrations create their own; table grants added). Then the usual path: `supabase db push --db-url postgresql://postgres:…@127.0.0.1:54399/postgres?sslmode=disable` (after a `--dry-run`).
Result: **all 62 migration versions applied cleanly in order; `supabase_migrations.schema_migrations` = the 62 files in `supabase/migrations/` exactly (diff empty); a second `db push --dry-run` reports "Remote database is up to date."** The dev DB (after applying `…130000` via psql and recording its ledger row) and the replay DB have **identical hashes for 185 catalog objects** touching this work (definitions + ACLs of 19 functions, policies built on `is_org_*`/`has_permission`, `check_audit_action`).
Limits: the `storage` seeding is a documented prerequisite, not part of the migrations; the container was removed afterwards (reproduce with the commands above). The dev DB's ledger had never recorded `20261004120000` (owner portal) and does not contain that schema — I did not run `migration up` against it (it would have applied that unrelated 48 KB migration); the two Phase 1/1.1 ledger rows were inserted by hand there.

## 5. Item 6 — write-safety guard

`tests/helpers/local-target.ts` (single definition) + `tests/setup/local-only-guard.ts`, registered as a vitest `setupFiles` entry in `vitest.config.ts`: `@supabase/supabase-js` `createClient` is wrapped so **any client built for a URL that is not `http://127.0.0.1|localhost:54321` (or the unroutable dummy port 1 used by unit runs) throws before the first request** — covering the ~30 existing suites and app code they import, with no per-file edits. Refusal message contains host only (never keys, credentials, path or query). `tests/local-target-guard.test.ts` (15) pins accepted/refused URLs (hosted `.supabase.co`, wrong scheme/port, embedded credentials, look-alike hosts, empty) and the no-secret-echo property. *Demonstrated:* `final-hardening.integration.test.ts` and `pgtap.integration.test.ts` run with the default `.env.local` (remote project) are refused immediately: `Refusing to run: test target <host> is not a known local Supabase API…`, no request made. Limits: it guards the Supabase JS client, not raw `fetch`, `docker exec psql` (local by construction) or Playwright e2e.

## 9. Further gaps found (not fixed; scope not expanded)
1. **Membership ≠ permission on reads (P1):** with `is_org_member` fixed, *any active member* still reads many financial/operational tables regardless of role. Measured in a rolled-back local transaction: a user whose only permission is `operations.gates.view` can select the organization's `chart_of_accounts` and `banks` rows; `list_projects` (WIP/budget figures) only requires membership. Needs permission-keyed policies per table.
2. `has_permission(p_user_id, …)` can be called by any signed-in user with an arbitrary user id (permission probing); it does not check organization status (SUSPENDED/ARCHIVED), unlike `has_financial_permission`.
3. Auth sessions are not revoked on suspension; the DB cuts access immediately but tokens live until expiry.
4. `verify_financial_audit_chain`: a NULL `auth.role()` (direct DB session) passes its guard; not reachable via the API.
5. Other `SECURITY DEFINER` functions callable by `authenticated` without an in-body identity check, outside this scope: `get_entitlement`, the `*_enabled(org)` feature checks, `post_fx_difference`, `post_supplier_invoice_in_currency`, `run_due_schedules`, `get_owned_unit_lease_renewal_status` — each needs a line-by-line review.
6. `trial balance` is period-only (no carried-forward opening balance); year-end close still unimplemented.
7. `tenant-dashboard.tsx` ignores the `get_trial_balance` error, so unauthorized users see zeros.
