# Task 10 — the remaining permission-test timeouts: diagnosis and PROPOSED fix (isolated stack only, 2026-10-14)

**Status: the proposal below was APPROVED for the three tables and applied as migration `20261017100900` (results: `final-run-after-rls/RESULT.md`). A second refinement (admin check as an InitPlan) found afterwards is proposed in `refinement-proposal.md` and NOT applied. The text below is the original diagnosis, kept as written; one claim in it is corrected there: the platform-admin branch is NOT evaluated once, it is called per row.**

## 1. What fails and why (measured)
| failing test | what it reads | measured |
|---|---|---|
| `membership-status-access` (6 tests) | `select count(*)` (exact) on 7 tables + 3 views for 4 principals; the first failure is `chart_of_accounts` | quiet machine, staff member of its own organization: `chart_of_accounts` **5.7–8.5 s** (13,473 rows), `fiscal_periods` **5.5–8.5 s** (12,626 rows) against the 8 s limit of role `authenticated`; owner and stranger the same order (`probe-quiet-rerun.md`). The upper end crosses 8 s, so the test fails whenever the machine is a little busy. |
| `owner-statement-settlement` "never hides a due" | owner session `from("dues").select("id")` | `dues` 1.0–1.5 s on a quiet machine (1,096 rows); readings of 4.6–6.8 s were taken under other load earlier. The test timed out once (57014). |
Honest note on the numbers: they swing by 4–6× with machine load. The first full probe (`probe-tables.md`, 16–40 s for `chart_of_accounts`) was taken while I was measuring a 23 GB folder on the same disk and is NOT representative; the quiet rerun is. In the prototype run the current policies took 6–46 s for the same count, so absolute "old" values are unreliable; the contrast with the new policies is the evidence.

## 2. Cause
* The policies call a `STABLE SECURITY DEFINER` function **for every row they scan**: `chart_of_accounts_select_permission` → `has_any_permission(organization_id, ARRAY[~25 keys])`; the second permissive policy `chart_of_accounts_manage` (command ALL, so it also applies to SELECT) → `has_permission(...)` **and** `organization_is_active(...)`; the same shape for `fiscal_periods`; `dues` has five permissive policies.
* Those functions carry `SET search_path` and `SECURITY DEFINER`, so Postgres can neither inline nor hoist them; each call is a full invocation that runs its own queries over `organization_memberships`, `user_role_assignments`, `roles`, `role_permissions` (296,000 rows) and `permissions`.
* Per-call cost, 13,473 rows of `chart_of_accounts`, argument varying per row (`micro.sql`): scan only 6 ms; `is_platform_admin` 221 ms (16 µs per call); `has_permission` **2,577 ms (191 µs per call)**; `has_any_permission` 2,520 ms (187 µs); `organization_is_active` 174 ms (13 µs). Two permission checks per scanned row ≈ 5 s for this table — matching the measured 5.7 s.
* Cost therefore scales with **the total number of rows in the table across all tenants**, not with what the principal may see (a permitted staff member sees 26 rows and still pays for 13,473). This is the same mechanism as the views fixed in Task 8, now in the base tables' policies.
* Owner on `dues` (`micro-dues.sql`): `work_order_cost_member_can_read_due(dues.*)` costs **0.9 s for 1,096 rows (0.82 ms per row)**, `has_permission` 0.27 s, the ownership sub-select and `organization_is_active` ≤ 0.03 s. That one function dominates the owner's read of `dues`.
* Scope: **86 tables / 111 policies** use `has_permission` / `has_any_permission`.

## 3. Proposed fix (NOT applied) and its prototype
Replace the per-row call by a set computed once per statement: a function `orgs_with_permission_keys(text[])` returning the caller's own organizations where an ACTIVE membership and a tenant-scoped role hold any listed key (identity only from `auth.uid()`, same authority model as `has_permission`/`has_any_permission`), and write the policy as `(auth.uid() is not null and is_platform_admin(auth.uid())) OR organization_id IN (SELECT orgs_with_permission_keys(ARRAY[...]))` — a hashed sub-plan evaluated once. The platform-admin branch stays in the policy (constant argument, evaluated once). No grant is widened; `organization_is_active` stays as an extra AND.
**Prototype, in `scratch_rls` only** (a copy of the stack; `rls_prototype.py`, `prototype-result.md`): the policies of `chart_of_accounts` (select + manage), `fiscal_periods` (select + manage) and `dues_select_permission` were rewritten there. Visible ids per principal and table, old vs new, both directions: **0 rows only in new, 0 only in old** for 21 principals (8 staff, 8 owners, 4 invited/suspended members, 1 stranger; 208 / 192 / 188 rows seen in total). `count(*)`: `chart_of_accounts` staff 30–46 s → 0.5–0.7 s, stranger 6–18 s → 0.5–1.6 s; `fiscal_periods` staff 25–43 s → 0.8–1.0 s, stranger 9–32 s → 0.4–0.7 s; `dues` staff 0.8–1.5 s → 0.9–1.3 s (no gain: it was not slow for staff), stranger 3.1–5.1 s → 0.8–1.4 s. Coverage limits: the principals see few rows; no platform admin existed in the data (the platform-admin branch was not exercised); only 3 of 86 tables were prototyped.
**Not covered by this proposal:** the owner's `dues` read is dominated by `work_order_cost_member_can_read_due` (0.82 ms per row), which is an owner-route function, not a permission check. It needs its own rewrite (same idea: compute the caller's readable work-order-cost dues once). The settlement test's flake stays open until that is decided.

## 4. What approval would involve
1. A forward migration adding `orgs_with_permission_keys` (EXECUTE for `authenticated` and `service_role` only; update `tests/security-function-grants.integration.test.ts` allowlist) and rewriting the chosen policies, starting with `chart_of_accounts`, `fiscal_periods` and `dues`.
2. An equivalence test in the style of `tests/financial-views-equivalence.integration.test.ts`: old vs new policy rows for staff, owners, invited / suspended / stranger, plus a platform admin and a cross-tenant case; the null-organization case is checked per table (`organization_id IN (...)` is false for NULL where the old function returned true for platform admins).
3. A decision on how many of the 86 tables to convert; each one is a security-sensitive change and needs the same proof.
4. No change to the global timeout. Until then `membership-status-access` fails on this stack whenever the machine is busy; that is recorded as an environment/RLS-cost failure, and a green re-run does not close it.
