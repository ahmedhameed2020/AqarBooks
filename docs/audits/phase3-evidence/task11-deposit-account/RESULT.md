# Deposit-account rule — local result (isolated stack only; no commit, push, deploy or production access)

## The rule
A receipt's deposit account must be: ASSET, active, not a group, **and the GL account of an ACTIVE cash box or ACTIVE bank account of the SAME organization**. It is not a block on the code 1130: 1130 is refused because nothing links it; any other unlinked asset account (1140, 1210…) is refused the same way; an account that is linked is accepted whatever its code (test: 1140 becomes valid when a cash box points at it and invalid again when that box is deactivated).

## What changed (proposed migration `20261018100000_deposit_account_cash_or_bank.sql`, 7,687 bytes, SHA-256 `9c0a6cbd97eb9e745f5ded174295ea4d3ba2488e80711fa154ccd22717e896e4`)
* `deposit_account_is_valid(org, account)` — the single statement of the rule; EXECUTE for `service_role` only (users cannot probe accounts of an organization).
* `list_deposit_accounts(org, resort)` — what the receipts screen offers: exactly the accounts the rule accepts; an empty set (not an error) for a caller without `receivables.payments.create`; anon has no EXECUTE.
* `record_payment` and `record_advance_payment` (the two receipt entry points callable by users) refuse with `DEPOSIT_ACCOUNT_INVALID` (SQLSTATE 22023) before anything is posted. Signatures, owner and grants unchanged.
* UI (`finance/payments/page.tsx`, `payments-dialog.tsx`): the deposit select is fed by `list_deposit_accounts`; when it is empty the dialog says why and what to do. The server stays the guard — the screen list is a convenience.
* Messages: `DEPOSIT_ACCOUNT_INVALID` added to `lib/finance/customer-advances.ts` (code list + ar/en text). Types: `lib/supabase/types.ts`.

## What does NOT change
* No data is read or written by the migration (functions only: no DML, no table/column change, no backfill) — asserted by a test that scans the migration text.
* Receipts already posted, and their journal entries, are untouched.
* The cashier-session check `DEPOSIT_ACCOUNT_MISMATCH` stays (it runs after this one). A cashier collection uses the session cash box's own GL account, so it passes while the box is active.
* `post_payment_internal` / `post_advance_payment_internal` and the online-payment path (clearing account validated by its own trigger, posted by a trusted caller with no user): unchanged.
* `clear_incoming_cheque` deposits to the cheque's bank account GL account: passes while that bank account is active (a deactivated bank account would now refuse clearing — noted, not changed).
* A retry of an already-posted receipt (same idempotency key) returns the stored receipt and is not re-validated (tested after deactivating the cash box).

## Effect on legacy accounts that were never linked (measured on the isolated stack, 1,189 test organizations — NOT production)
* Only 9 organizations have any active cash box or bank account; 1,180 do not. A new receipt in any of those 1,180 is refused until the organization links its cash account (`create_cashbox`) or adds a bank account. **Nothing is linked automatically** (no backfill was written, on purpose: choosing which account is "the till" is the organization's decision).
* Historical receipts by deposit account (1,204 with one): 1110 unlinked 1,186 (434 organizations); 1130 unlinked 4 (2 organizations); 1120 linked 3, unlinked 2; 7 receipts on fixture-created asset accounts. These stay valid and untouched; only NEW receipts are subject to the rule.
* For production the same measurement is prepared as read-only queries (`docs/audits/release-plan/production-readonly-checks.sql`, section 6), not run. Query 6c lists organizations with receipts in the last 90 days on an unlinked account: each needs a cash box or bank account **before** this migration is deployed, otherwise its cashier loses the ability to record receipts the moment it is applied.

## Second pass (2026-10-16): link rules, cheques, catalog verify, missing test files
**Migration now 10,729 bytes, SHA-256 `3e6aa7084e922170a510eb1947f8e45e7916c05d60670a93fa2c35d4d0db6778`** (re-pinned in the guard). Gap found by reading the code: `create_cashbox` checked only the category; the app inserts into `cashboxes` / `bank_accounts` directly under the `*_manage` RLS policy whose WITH CHECK checks the permission only, and the foreign key accepts an account of ANOTHER organization. Anyone holding `finance.accounts.manage` could therefore link a cash box to 1130 and make it a valid deposit account. The cash box and bank forms offer only cash-like accounts.
