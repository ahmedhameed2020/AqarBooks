# خطة فصل التطوير عن الإنتاج (بدون حذف بيانات)

**الهدف:** يبقى المشروع السحابي `ataslxkc…` بيئة الإنتاج؛ وتنتقل التطويرات والاختبارات اليومية إلى r6 المحلي. **لا حذف** لأي بيانات اختبار أو إعدادات؛ الأرشفة تصدير فقط.

**الوضع الحالي (أدلة):** `.env.local` و`.env.production` و`supabase/.temp/project-ref` كلها تشير إلى نفس المشروع السحابي؛ الاختبارات الآلية محمية بالفعل عبر `tests/helpers/local-target.ts` (ترفض غير loopback وترفض 54321).

## الخطوات (ينفذها المالك/فريق التطوير — تغييرات بيئة محلية)

1. **قبل أي تغيير:** جرد قراءة فقط للبيانات السحابية (انظر استعلامات `production-identity-assessment.md` §3) + لقطة إعدادات Auth/Storage.
2. **توجيه تطوير Next إلى r6:** إنشاء `.env.development.local` (مهمل في git) يحمل:
   - `NEXT_PUBLIC_SUPABASE_URL=http://127.0.0.1:58461`
   - `NEXT_PUBLIC_SUPABASE_ANON_KEY` لمفتاح r6 المحلي
   - `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` نفس المفتاح
   - `SUPABASE_SERVICE_ROLE_KEY` لمفتاح r6
   - مسبوقًا بـ`ISOLATED_CONTRACT=r6`, `R6_DB_CONTAINER=g0r6-db`, `R6_API_CONTAINER=g0r6-kong`
   أولوية Next: `.env.development.local` يتقدم على `.env.local` في `next dev`.
3. **التحقق:** تشغيل `npm run dev` ثم فحص أن الطلبات تذهب إلى `127.0.0.1:58461` (‏Network tab أو healthcheck) — لا اتصال بـ`ataslxkc…`.
4. **الحفاظ على `.env.local` و`.env.production` كما هما** (الأول للتجارب السحابية اليدوية عند الحاجة، والثاني نشر الإنتاج). لا تُعدّل قيمهما في هذه الخطوة.
5. **الـCLI:** `supabase/.temp/project-ref` يربط CLI بالسحابة. قرر: (أ) إبقاء الربط لعمليات الإنتاج المصرح بها فقط، مع قاعدة «لا db push/reset من جلسة تطوير»، أو (ب) `supabase unlink` محليًا وإعادة الربط عند الحاجة. لا تفعل هذا تلقائيًا.
6. **الاختبارات:** الحاجز قائم؛ أضف عند الحاجة `LOCAL_SUPABASE_API_PORTS=58461` في سكربتات rm6 فقط. لا تمنح أي opt-in لمشروع سحابي (الحاجز يرفض غير loopback أصلًا).
7. **أرشفة بيانات الاختبار السحابية (بدون حذف):** تصدير النتائج من الاستعلام إلى CSV/ملف أدلة، ثم قرار مالك منفصل بأي معالجة.
8. **توثيق القرار** في `docs/progress/decisions/` باسم تاريخه.
