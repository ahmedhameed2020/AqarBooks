# db-security-reviewer — مراجعة RLS لدوري authenticated/anon

**التاريخ:** 2026-10-31 · **الوضع:** قراءة فقط على كود/ترحيلات SQL (بلا اتصال بقاعدة حية) · **الغرض:** البندان 7 و9 من `docs/progress/launch-checklist.md`
**طريقة العمل:** وكيل `db-security-reviewer` (plan) ضمن نظام التفويض في `AGENTS.md`، ثم تحقق المنسق من الأدلة الحرجة يدويًا (انظر الملحق).

## 1. النطاق والمنهج

جرد شامل عبر 103 ملفات في `supabase/migrations/`: 230 بيان `create policy`، ‏97 تفعيل RLS أساسي + 38 لاحقًا (**صفر تعطيل RLS في أي ترحيل**)، جرد كامل للـ grants/revokes، ‏490 دالة SECURITY DEFINER (68 ملفًا)، كل `security_invoker` للمشاهد. مقاطعة متقاطعة ثلاثية: الجداول الممنوحة × المفعَّل RLS، المُنشأة × المفعَّلة، وقراءة نصوص السياسات عند الأسطر الدقيقة.

## 2. الحكم على القرار المسجل (البند 7)

**قرار 2026-10-30 (Batch 1B) — «لا سياسات UPDATE/DELETE لدوري authenticated/anon على journal_entry_lines؛ الكتابة عبر RPCs من نوع SECURITY DEFINER» — سليم في SQL، وأقوى مما سُجّل: لا توجد سياسة INSERT أيضًا.**

سلسلة الأدلة:
- RLS مفعَّل: `20260821105505_baseline.sql:17114`؛ لا ترحيل يعطله أبدًا (grep صفر نتائج).
- سياسة واحدة فقط عبر كل الترحيلات، SELECT فقط دائمًا: `journal_entry_lines_select_member` (`:17117-17119`) ← أُسقطت وأُعيدت `journal_entry_lines_select_permission` (`20261009140000:114-116`) ← عُدّلت أدائيًا (`20261017101100:24-32`)، وترويسة الترحيل تنص صراحة: «سياسة SELECT واحدة؛ لا INSERT/UPDATE/DELETE؛ الكتابة مرفوضة افتراضيًا وتتم عبر دوال SECURITY DEFINER».
- لا ترحيل لاحق يغيّر ذلك بصمت؛ كل المراجع اللاحقة قراءات داخل دوال أو إدخالات داخل دوال مالكة.
- ‏`GRANT ALL … TO anon/authenticated` (`baseline:20695-20696`) خامل للـ DML لأن RLS يرفض أي أمر بلا سياسة مسموحة. الداخليات الكاتبة service_role-only مع `REVOKE ... FROM authenticated` (`baseline:21168-21172`).

## 3. النتائج

| # | الخطورة | الكائن | النتيجة |
|---|---|---|---|
| F1 | **IMPORTANT** | RPCs المُبوابة بـ `has_permission` مقابل `proveTenantPermission` | **من:** PLATFORM_SUPER_ADMIN يستخدم JWT الخاص عبر PostgREST. **كيف:** قاعدة البيانات تعطي مديري المنصة تجاوزًا مقصودًا في `has_permission` (فرع `is_platform_admin`)، بينما طبقة التطبيق تستبعدهم فئويًا (`lib/auth/authorize.ts:113-115`). لذا `proveTenantPermission` ليس حدًا أمنيًا أمام مديري المنصة: دوال مثل `reverse_journal_entry` (`20261019100100:335`) و`create_fiscal_year` (`:429`) و`designate_retained_earnings_account` (`20261019100000:123`) تبقى قابلة للاستدعاء المباشر من مدير منصة لأي مستأجر. (الحالة الأشد حساسية `close_fiscal_year` أُغلقت بفحص عضوية إضافي بقرار مالك موثق `:270-277`.) دوال `has_financial_permission` غير متأثرة. **المعالجة:** قرار مالك — إما توثيق «مدير المنصة = صلاحية كاملة على المستأجرين على مستوى القاعدة»، أو إضافة فحص العضوية نفسه للدوال المتبقية. |
| F2 | MINOR | `user_role_assignments_manage` (`baseline:17690`) | السياسة الإدارية الوحيدة الناقصة شرط `organization_is_active` الموجود لدى نظيراتها. حامل `tenant.users.manage` في منظمة موقوفة يستطيع تعديل تعيينات الأدوار (العضوية نفسها ما زالت مطلوبة، فالأثر محدود). |
| F3 | MINOR | `accsys_stage.materialize()` / `materialize_operations()` | آلية استيراد Legacy متبقية: SECURITY DEFINER بلا فحص تفويض إطلاقًا، تكتب قيودًا وسطورًا لمنظمة `is_demo` ثابتة، وتُعطّل محفزات الاستحقاقات. **غير قابلة للوصول من العميل** (لا `GRANT USAGE` لـ anon/authenticated على المخطط). المعالجة: إسقاط الآلية بعد اكتمال الاستيراد وإضافة المخططات لمسح فحص الصلاحيات. |
| F4 | MINOR | عدم تماثل القراءة: `journal_entries` مقابل `journal_entry_lines` | بعد Batch 1B تُقرأ السطور بخمسة مفاتيح بينما صف القيد الأم يتطلب مفتاحين فقط (`20261017101100:18-32`). حامل `finance.accounts.view` يرى مبالغ السطور دون ترويسة القيد. حميد لكنه غير متسق. |
| F5 | MINOR (وضع منهجي) | الافتراضي: كل دالة جديدة تُولد قابلة للتنفيذ من `authenticated` | الحماية تعتمد على انضباط REVOKE لكل دالة — منفَّذ جيدًا ب assertions واختبار مسح (`tests/security-function-grants.integration.test.ts`). الخطر المتبقي دوال مستقبلية بلا مراجعة. التوصية: assertion في زمن الترحيل يفشل عند أي دالة SECURITY DEFINER جديدة تكتب بيانات مستأجرين وقابلة للتنفيذ من `authenticated` بلا حارس داخلي. |

**لا BLOCKER.** صدت عمليات الصيد الكلاسيكية:
- **جداول fail-open:** لا شيء. كل جدول عام أُنشئ بعد الأساس له `ENABLE ROW LEVEL SECURITY` في ترحيله (38 تفعيلًا مقابل الإنشاءات). الجداول المفعَّلة بلا سياسات تفشل مغلقة (deny-by-default)، مثل `payments` (قراءة فقط؛ الكتابة عبر `record_payment` المحروس فقط).
- **`auth.uid()` بلا نطاق منظمة:** فقط في الكتالوجات العامة (`permissions`، `plans`، القوالب...) — لا بيانات مستأجرين.
- **المشاهد:** كلها `security_invoker=true`.
- **Anon:** صفر دوال قابلة للتنفيذ (بassertion)؛ ‏`GRANT ALL TO anon` يُحيّده RLS في كل الجداول.
- **مفتاح service_role:** لا يظهر إلا في `lib/supabase/admin.ts` (‏`server-only` موثق «bypasses RLS — كل مستدعٍ يجري تفويضه الخاص») و`lib/env/server.ts`؛ عملاء العميل/الخادم يستعملون anon key.
- **جرعات محفزات** تمنع تعيين الأدوار العابر للمستأجرين وأدوار `PLATFORM_SUPER_ADMIN` المنظمة وصلاحيات `platform.*` على أدوار المستأجرين. `replace_role_permissions_atomic` تتطلب فاعلًا وتفشل مغلقة وهي service_role-only. `fiscal_year_closings` كتابتها ممنوعة حتى من service_role (النمط الذهبي).

## 4. خارج النطاق — لم يُتحقق منه

- **لا قاعدة حية:** كل ما سبق هو الحالة التراكمية كما تصرح بها الترحيلات. التطبيق الفعلي على r6 ومطابقة `pg_policies` توصية رخيصة تالية.
- ليست كل الـ 490 دالة SECURITY DEFINER مدققة سطرًا بسطر (الدوال التشغيلية: بوابة/صيانة/مرافق فُحصت على مستوى السياسات والمنح).
- إعدادات منصة Supabase (Auth، حدود المعدل، `config.toml`، سياسات التخزين خارج دلو الصيانة).
- تفويض Server Actions في طبقة التطبيق خارج `authorize.ts`، و middleware، والأسرار خارج مفتاح service key.
- الأداء/DoS (عمل timeout الـ 8 ثوانٍ في Batch 1B دُقق بقراءة قياسات الترحيل لا بإعادة تشغيل).

## 5. توصية القائمة

- **البند 7 ← ✅ على r6** بهذه المراجعة كدليل: القرار منفذ تنفيذًا سليمًا ومتسقًا في SQL وأقوى مما سُجّل.
- **البند 9 ← يبقى ⚠️:** هذه المراجعة تغطي سطح RLS/الصلاحيات/أسرار RPC فقط. يحتاج: مراجعة Server Actions والأسرار الأخرى + مطابقة القاعدة الحية أعلاه.
- **F1 يحتاج قرار مالك صريحًا قبل الإطلاق** — إنه خيار سياسة لا عيبًا.

## ملحق 2: مطابقة القاعدة الحية g0r6 (2026-10-31) — المنسق

استعلامات read-only مباشرة على حاوية `g0r6-db`:

- **RLS مفعَّل** على الجداول السبعة الحساسة كلها (`rowsecurity = t`) ✓
- **`journal_entry_lines`**: سياسة واحدة فقط `journal_entry_lines_select_permission` — SELECT، أدوار {public} ✓ (لا INSERT/UPDATE/DELETE كما صرحت الترحيلات)
- **`payments`**: سياستا SELECT فقط ✓
- **`fiscal_year_closings`**: سياسة SELECT فقط ✓
- **تنفيذ الدوال الأربع من `authenticated`**: كلها `true` — ما يؤكد مقدمة F1 (قابلة للاستدعاء بـ JWT مستخدم)

الخلاصة: الحالة التراكمية المصرَّح بها في الترحيلات مطابقة للواقع على g0r6 للكائنات المفحوصة. فجوة «بلا قاعدة حية» المعلنة في القسم 4 أُغلقت لهذه الكائنات.
