## 1. membership-status-access.integration.test.ts

**النتيجة الأصلية (run 1/2/3/4/5/6):** 16 نجاحًا و1 فشل من 17.
الفشل: `activation result: expected { ok: false, error: 'forbidden' } to deeply equal { ok: true }` عند السطر 184.

**التشخيص المثبت بالدليل:**

- التتبّع المؤقت داخل `proveTenantPermission` (ثم أُزيل بـ `git checkout`، والملف مطابق لـ HEAD بفرق صفري) أظهر أن كل الفحوص نجحت حتى الاستعلام عن `permissions`، فجاء الرد: `permErr = "An invalid response was received from the upstream server"` و`permMatch = null`، فأعادت الدالة `forbidden`.
- سجلات `g0r6-kong` تُظهر لكل طلب من هذا النوع: `upstream sent too big header while reading response header from upstream` على المسار `GET /rest/v1/permissions?select=id&id=in.(…)`.
- السبب: الاستعلام يحمل قائمة UUID طويلة (نحو 100 معرّف لدور المالك)، فتتضمن ترويسات الرد (ومنها `Content-Location` التي يعيد PostgREST فيها نص الاستعلام) حجمًا يتجاوز حجم buffer الافتراضي في nginx لدى Kong.
- صلاحيات المالك سليمة: العضوية `active`، وإسناد `TENANT_OWNER` موجود، و`tenant.users.manage` ممنوح في كل أدوار TENANT_OWNER (2754 صفًا للدور)، ولا يوجد تكرار في `permissions`.

**إعداد البوابة الذي طُبّق داخل حاوية r6 فقط:**

| البند | القيمة |
|---|---|
| الحاوية | `g0r6-kong` (لم تُعَد إنشاؤها ولم تُعَد تشغيلها) |
| الملف | `/usr/local/kong/nginx.conf` |
| الموضع | داخل كتلة `http {` قبل `include 'nginx-kong.conf';` |
| القيم المضافة | `proxy_buffer_size 32k;` · `proxy_buffers 8 32k;` · `proxy_busy_buffers_size 64k;` |
| النسخة الاحتياطية | `/usr/local/kong/nginx.conf.bak-r6` داخل الحاوية |
| أمر الاختبار | `/usr/local/openresty/nginx/sbin/nginx -t -p /usr/local/kong -c nginx.conf` (نجح) |

**التحقق بعد التطبيق:**

- ملف membership: **17/17 نجاحًا، 0 فشل** (`run7_tests_membership-status-access.integration.test.ts.json`).
- عدد أخطاء `too big header` منذ وقت إعادة التحميل: **0**، وعدد طلبات `permissions?select=id` المسجلة منذ وقتها: **0** (الرقم 2 المسجل سابقًا كان قبل إعادة التحميل).

**تحذيرات:**

- التعديل موجود داخل الحاوية فقط؛ **يضيع عند إعادة إنشاء `g0r6-kong`**، ويجب إعادة تطبيقه بالأوامر أعلاه قبل أي تشغيل جديد.
- هذا الإصلاح لا يثبت صحة منطق التفويض كله؛ يثبت فقط أن الفشل المرصود كان من البوابة.
