# تسليم مرحلة تصنيف الإيراد والإنفاذ الضريبي

- **التاريخ:** 2026-08-18
- **الحالة:** المرحلة **مكتملة تقنيًا ومتوقفة عند قرار بشري واحد**
- **آخر تثبيت:** الإنفاذ لكل مؤسسة ومراقبة فجواته

## ما شُحن

| التثبيت | المضمون |
|---|---|
| `ddd8577` | ADR 0002 — `organizations.tax_id` مصدر الهوية الضريبية |
| `b33b659` | أساس التصنيف: قاموس الأنواع، القواعد المؤرَّخة المُصدَّرة، بصمة القرار |
| `b719dc5` | شاشة مراجعة الربط + سجل تدقيق |

| `6a7d65e` | مخرج الطوارئ مرصود: أثر باقٍ، سبب إلزامي، ومراقبة تقيس الفجوة |

**الاختبارات:** 74 اختبارًا تكامليًا + 12 اختبار عرض حي. `tsc` والبناء نظيفان.

## الثوابت التي تحملها القاعدة الآن

**لا يُشتق تصنيف ضريبي من اسم.** 352 نوع مستحق نصي حر عبر 335 مؤسسة، والربط
يدوي صريح يبدأ `REVIEW_REQUIRED` ويحتاج اعتمادًا.

**القاعدة المعتمدة لا تُعدَّل، بل تُخلَف.** قيد استبعاد يمنع التداخل الزمني،
والاختيار بتاريخ المعاملة لا الترحيل، والبصمة تستثني `effective_to` فلا تفسدها
الخلافة.

**القرار التاريخي لا يتحرك.** لا تعديل ولا حذف؛ التصحيح قيد عكسي بسببه، والسلسلة
خطية بقيدين فلا يوجد رأسان نشطان.

**المصدر هو الحقيقة.** مُعامل واحد؛ المؤسسة ونوع المستحق وتاريخ المعاملة تُقرأ
من صف `dues`، فلا يستطيع مستدعٍ ختم قرار لمؤسسة أخرى ولا تمرير تاريخ ترحيل.

**الإنفاذ ذري ولا يُتجاوَز.** trigger على `dues` — أي إدراج من أي محرك حاضر أو
مستقبل يمر به، وفشل القرار يسحب المستحق والقيد معه.

## ما يبقى مفتوحًا — بصراحة

**١. التفعيل يعمل إلى الأمام فقط — والفجوة صارت مرئية وشرطًا لا يُتجاوَز.**
المستحقات القائمة لن يكون لها قرار ضريبي ما لم يُستدرك ذلك عمدًا. ولم أبنِ
الاستدراك لأن معالجة المستحقات السابقة قرار محاسبي لا تقني: أتُصنَّف بقواعد اليوم
أم بقواعد تواريخها؟

لكن التأجيل لم يبقَ صامتًا. `get_tax_decision_coverage` تقيس الأثر — العدد والمدى
**والمبلغ** — و`set_tax_enforcement` ترفض التفعيل ما لم يذكر المستدعي العدد
**مطابقًا** للواقع، فلا يمرّ الإقرار بالتخمين ولا بنسخ رقم قديم. والفجوة المقبولة
تُختم في سجل التدقيق لحظة قبولها بفاعلها ومداها ومبلغها.

**٢. لا شاشة للتفعيل.** خارج النطاق باعتمادك. التفعيل اليوم عبر RPC فقط.

**٣. أنواع Supabase المولَّدة ليست متزامنة** —
[تذكرة قائمة](../tickets/supabase-types-regeneration.md)، 158 خطأ عند إعادة
التوليد الكاملة.

**٤. إخفاقان في E2E لا علاقة لهما بهذه المرحلة:**
`owner-portal-online-payment-fawry` يحتاج `FAWRY_SECURE_KEY` في `.env.local`
(شرط بيئة لا خلل)، و`owner-portal-invite` يفشل في صفحة قبول الدعوة — والملف لا
يذكر `einvoice` ولا `tax_` ولا `dues` إطلاقًا، فتغييرات هذه المرحلة لا تصل إليه.

## دفتر تشغيل الطيار — جاهز للتنفيذ فور وصول كتلة الاعتماد

الترتيب السباعي كما اعتمدتَه. **لا يبدأ أي منه قبل تعبئة
[كتلة الاعتماد](../decisions/0008-signoff-block.md).**

```sql
-- ١) إدخال المعتمد فقط — لكل قاعدة، مسودة ثم اعتماد.
select create_tax_rule_draft(
  'EG', 'MANAGEMENT_FEE', 'TAXABLE', 14, '<تاريخ السريان المعتمد>',
  'BY_CUSTOMER_TYPE', '<مقدّم الخدمة المعتمد>', '<المرجع القانوني>');
select approve_tax_rule('<rule_id>');   -- مشرف المنصة وحده
```

```sql
-- ٢) الجاهزية لمؤسسة sandbox واحدة — يجب أن تعود فارغة.
select * from check_tax_enforcement_readiness('<sandbox_org_id>');
```

```sql
-- ٣) و٤) الربط الصريح ثم اعتماده — لكل نوع مستحق نشط.
select set_due_type_revenue_nature('<due_type_id>', 'MANAGEMENT_FEE', '<المرجع>');
select approve_due_type_revenue_nature('<mapping_id>');
```

```sql
-- ٤أ) تقرير أثر الفجوة التاريخية — إلزامي قبل التفعيل، ويُرفَع للمراجعة.
select * from get_tax_decision_coverage('<sandbox_org_id>');
```

```sql
-- ٥) التفعيل لتلك المؤسسة وحدها، مع إقرار صريح بعدد المستحقات غير المصنَّفة.
--    عدد مخالف للواقع يُرفض كغيابه.
select set_tax_enforcement(
  '<sandbox_org_id>', true, 'طيار مرحلة أولى — الفجوة التاريخية مُقَرَّة',
  <dues_without_decision من الاستعلام أعلاه>);
```

**٦)** إنشاء مستحق في المؤسسة والتحقق من ظهور المستحق والقيد والقرار معًا؛ ثم
إنشاء مستحق بتاريخ لا تغطيه أي قاعدة والتحقق من **عدم بقاء** مستحق ولا قيد.
(هذان السيناريوهان مُغطّيان آليًا في `tests/tax-enforcement.integration.test.ts`،
والتنفيذ اليدوي هنا لتأكيد السلوك على بيانات المؤسسة الفعلية.)

**٧)** لا توسيع قبل تقرير مستقل. ولمراقبة أي إيقاف:

```sql
select * from list_tax_enforcement_lapses();   -- مشرف المنصة وحده
```
