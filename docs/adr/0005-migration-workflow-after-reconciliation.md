# ADR 0005 — استئناف الـmigrations بعد مصالحة السجل

- **الحالة:** **معتمد — موقَّع.** · Rev 2.8 · commit `960f3f2f`
- **التاريخ:** 2026-08-22
- **الأثر:** كل migration بعد خط الأساس `20260821105505`
- **يسبقه:** [ADR 0004](0004-security-baseline-freeze.md) · Step 7 Production Execution Record · Step 8 Execution Record
- **الأدوات المرجعية:** Supabase CLI **2.78.1** — كل أمر ذُكر هنا تُحقِّق من وجوده وسلوكه مقابل هذا الإصدار، لا مقابل التوثيق وحده

> **هذه الوثيقة موقَّعة وسارية** اعتبارًا من 2026-08-22. وهي تُحدِّد **القواعد** التي
> يُنفَّذ تحتها أي نشر لاحق.
>
> **ومع ذلك: `supabase db push` على الإنتاج ما زال ممنوعًا.** التوقيع لم يرفع حظر
> ADR 0004، ولا يرفعه إلا اجتماع أمرين — اجتياز بوابة تفعيل Step 9 (§٦-أ-٢) **و** وجود
> تفويض migration مسمّى (§٣). انظر «بعد التوقيع» في نهاية الوثيقة.

## السياق

حظر ADR 0004 لـ`supabase db push` كان **مشروطًا** بنصّه: ممنوع «قبل معالجة الـmigration
drift رسميًا في Phase 2». تلك المعالجة تمّت وأُثبتت:

```
Step 5   خط الأساس أعاد إنتاج الإنتاج على مشروع فارغ — 16/16 فئة
Step 6   228 ملفًا انتقلت إلى الأرشيف، لا حذف ولا إعادة تسمية
Step 7   سجل الإنتاج 143 ← 144 ← صف واحد، transaction حذف فقط
Step 8   المرجع authoritative في المستودع يطابق واقع الإنتاج
```

وضع الإنتاج المقيس 2026-08-22: صف واحد، `20260821105505`/`baseline`، 3,331 عنصرًا،
943,910 بايت، canonical `7700b000…14ca`، ordered `967f5739…d425`، والفئات الست عشرة
دون تغيير. `migration list` يُظهر `{20260821105505}` محليًا وبعيدًا.

### التصحيح الجوهري في هذه المراجعة

Rev 1 من هذه المسوّدة قالت إن `db push` «يظل ممنوعًا كإجراء اعتيادي» ثم **لم تسمِّ ما
يحلّ محلّه**. كان ذلك خطأ تصميميًا: وثيقة تُعرِّف حدًّا ولا تقول ما بداخله تُعيد الاجتهاد
إلى المشغّل، وهو الشيء الوحيد الذي بُنيت هذه المنظومة لإلغائه.

التصحيح:

> **`db push` ليس ممنوعًا كآلية. الممنوع هو `db push` غير المحكوم.**

ADR 0004 منعه لأن تاريخ الـmigrations كان غير موثوق، لا لأن الأمر نفسه معيب. السبب انتهى.
والمسار القياسي من المورِّد — ملفات migration تُدفَع بـ`db push` الذي يقارنها بسجل
`supabase_migrations.schema_migrations` ويطبّق غير المطبَّق فقط — هو المسار الصحيح.
تعديلات SQL Editor أو Dashboard المباشرة هي ما يُنتج الـdrift أصلًا.

**لم نبنِ نظامًا غريبًا حول Supabase؛ أصلحنا التاريخ حتى نستطيع العودة إلى المسار الذي
صُمِّم له النظام، داخل بوابات أقوى مما كان.**

## ١. القرار — المسار المسمّى إلى الإنتاج

```text
Production migration mechanism
==============================

  supabase db push --dry-run --linked
          ↓
  mechanical preflight assertions          §٦
          ↓
  named human authorization                §٣
          ↓
  supabase db push --linked
          ↓
  post-apply verification                  §٦-ب
          ↓
  supabase migration list
  local set == remote set
```

وتُفصَل ثلاثة أمور فصلًا حادًّا، لأن خلطها هو ما أنتج الانحراف الأصلي:

```text
Authoring     supabase migration new <name>
Validation    بيئة تحقّق مُعاد بناؤها من خط الأساس        §٥
Deployment    supabase db push --linked  عبر البوابة فقط
```

## ٢. الأدوار

| الدور | المسؤولية | القيد |
|---|---|---|
| **Author** | يؤلّف SQL الـmigration فقط | لا يفوّض ولا ينفّذ على الإنتاج |
| **Reviewer** | يراجع SQL وأثره الأمني وأثره على البيانات | شخص غير الـAuthor |
| **Authorizer** | يمنح التفويض المسمّى (§٣) | يملك سلطة القرار على الإنتاج |
| **Operator** | ينفّذ الأمر المسمّى حرفيًا | لا يعدّل، ولا «يصلح ويكمل» |

**لأي migration مصنَّفة R1 أو R2 (§٧): لا يجوز أن يكون Author هو نفسه Reviewer وAuthorizer
وOperator.** الفصل ليس بيروقراطية؛ عيب `20260820190630` — الذي منح `authenticated` تنفيذ
تسع دوال داخلية — مرّ لأن أحدًا لم يقرأه بعينٍ أخرى، وكُشف بمقارنة تقريرَي advisor يدويًا.

## ٣. التفويض المسمّى

«مأذون» وحدها لا تكفي. التفويض وثيقة تحتوي **كل** ما يلي:

```text
Migration version        <14-digit>          ← واحدة بالضبط
Migration filename       <version>_<snake_case_name>.sql
Exact git commit SHA     <40-hex>
Target project ref       <ref>
Validation environment   <ref/identifier> + result
Dry-run result           النص الحرفي لما سيُطبَّق
Migration file SHA-256   <64-hex>                          §٤
Expected-delta manifest  <path>                            §٥
Expected-delta SHA-256   <64-hex>
  ويحتوي إلزاميًا قسمين:
    structural   ما يُتوقَّع تغيّره من الفئات، وما يجب ألا يتغيّر
    data-impact  إلزامي عند أي INSERT | UPDATE | DELETE | TRUNCATE:
                 نطاق الصفوف المتوقَّع مسّها، وتأكيدات/استعلامات
                 تُثبت الصحة — تُنفَّذ على بيئة التحقّق ثم على
                 الإنتاج في postflight (§٦-ب)
Authorized remote set    REMOTE_AUTHORIZED — القائمة المرتَّبة كاملة
Authorized remote digest <64-hex>                          §٦
Rollback classification  R0 | R1 | R2                       §٧
R1 recovery artifact     <path> + SHA-256   (إلزامي إن كان الصنف R1)
R2 backup identifier     <id>                (إلزامي إن كان الصنف R2)
R2 backup SHA-256        <64-hex>
R2 restore proof         مرجع إثبات الاسترجاع المُختبَر
R2 special authorization <مرجع التفويض الخاص المنفصل>
Reviewer                 <اسم>
Authorizer               <اسم>
Operator                 <اسم>
Authorization date       <ISO>
Authorized command       supabase db push --linked
```

**أي تغيّر في الـSHA أو في مجموعة الـmigrations بعد إصدار التفويض يُبطله.** لا يُعاد
استخدام تفويض «قريب بما يكفي»؛ يُصدَر تفويض جديد.

### العدد — migration واحدة لكل تفويض

```text
|AUTH| = 1        بالضبط، بلا استثناء
```

التفويض الواحد يغطي **نشر migration واحدة معلَّقة**. لا batch، ولا «مجموعة صغيرة»، ولا
«اثنتان مترابطتان». هذا أول workflow بعد الأزمة، والوضوح فيه أثمن من الكفاءة: نشر واحد
= صف واحد جديد في السجل = تفويض واحد = مسؤولية واحدة قابلة للتتبّع.

النشر الدفعي (batch) — إن لزم لاحقًا — يحتاج **تعديل ADR مستقلًا** يُعرّف دلالة الفشل
الجزئي داخل الدفعة. لا يُستنتج من هذا النص.

### ربط الـdry-run بالتطبيق

التفويض يوثّق نتيجة dry-run؛ لكن نتيجة قديمة لا تصف الحاضر. لذلك:

```text
يُعاد تشغيل  supabase db push --dry-run --linked
مباشرة قبل التطبيق، في نفس الـworktree، وبنفس:
    git commit SHA
    linked project ref
    local migration set

ويجب أن يكون خرجه مطابقًا حرفيًا للخرج المسجَّل في التفويض.

أي اختلاف — ولو سطرًا — ثم STOP · التفويض باطل · صفر كتابة
```

والأمر المطبَّق هو **نفس الأمر المفوَّض حرفيًا**، لا صيغة مكافئة ولا أمر أُعيد تركيبه.

## ٤. هوية الـmigration — قواعد صارمة

الصرامة هنا ليست ذوقًا: الأرشيف يحمل **٧ أسماء ملفات مشوّهة**، ونشأ الانحراف جزئيًا من
طوابع زمنية مولَّدة لا تطابق الملفات.

```text
الصيغة الوحيدة المقبولة
  <14-digit timestamp>_<snake_case_name>.sql

  version فريدة عالميًا
  اسم ملف مطابق للصيغة، بلا مسافات ولا محارف خاصة
  version واحدة جديدة لكل تفويض — |AUTH| = 1 (§٣)
  ممنوع تكرار version مرئية للـCLI
  ممنوع إعادة التسمية بعد النشر
  ممنوع تعديل migration مطبَّقة
```

### خط الأساس — غير قابل للتعديل نهائيًا

```text
20260821105505_baseline.sql
  IMMUTABLE FOREVER
  bytes   956400
  sha256  cf3de852cecc49d29e5d24c6bbb6afcebf8d65aeb994b684f5fc0a21f02790d7
```

أي بايت يتغيّر ← **STOP**. الملف دليل أُثبت على مشروع فارغ، لا مجرد مصدر.

### الثابت الدائم

> **Applied migrations are append-only history. Never edit, rename, delete, or rewrite a
> migration after it has been applied to any shared environment. Correct it with a new
> migration.**

هذا الثابت **دائم**، ولا تنتهي صلاحيته بانتهاء أي مرحلة.

## ٥. سُلَّم التحقّق

لا يُشترط إنشاء مشروع Supabase مدفوع جديد لكل migration. المطلوب بيئة **يمكن مسحها وإعادة
بنائها**، لا بيئة جديدة.

```text
1  إعادة بناء البيئة حتى حالة ما قبل الـmigration المعلَّقة
     خط الأساس + كل الـmigrations المطبَّقة سابقًا — دون المعلَّقة
     supabase db reset   (local)  |  إعادة بناء بيئة التحقّق

2  إثبات أن الحالة الموروثة قانونية — مقابل الحالة المقبولة الأخيرة
     N = 0   مقارن Step 5 المسترجَع: 16/16     ← خط الأساس وحده
     N > 0   بصمات PRE == ACCEPTED_STATE_N     ← آخر حالة قُبِلت (§٦-ج)

3  التقاط بصمات PRE
     الفئات الست عشرة + الثوابت الأمنية، كما هي قبل التطبيق

4  تطبيق الـmigration المعلَّقة على بيئة التحقّق

5  تأكيد الـEXPECTED DELTA
     الفرق بين PRE وPOST يطابق **بيان الـexpected-delta المسجَّل في التفويض** (§٣)
     لا «ما تُعلنه الـmigration» ضمنًا — البيان ملف مُجزَّأ بـSHA-256 ومُراجَع مسبقًا،
     يذكر صراحةً: ما يُتوقَّع تغيّره، وما يجب ألا يتغيّر

6  تأكيد الثوابت الأمنية الدائمة
     npm run test:security — 4/4، على بيئة التحقّق (§٥-ج)

7  تأكيد انعدام الـUNEXPECTED DELTA
     لا فرق في أي فئة لم تُعلنها الـmigration

ثم:
C  supabase db push --dry-run --linked   على الإنتاج — قراءة ومعاينة فقط
D  التفويض المسمّى                        §٣
E  supabase db push --linked              التطبيق
```

**لا يصل الإنتاج شيء لم يُطبَّق قبله على بيئة أُنشئت من خط الأساس نفسه.** هذا هو الثابت
الذي أثبتته Step 5، ولا يُستعاض عنه باختبار على جهاز مطوِّر.

> **مقارن Step 5 يصلح مرة واحدة فقط.** بعد أول migration مشروعة تُنشئ جدولًا أو فهرسًا
> أو دالة، لن تعود *الحالة السابقة* للـmigration التالية مساوية لخط الأساس — فاشتراط
> 16/16 عندها يفشل للسبب نفسه الذي أفشل الصياغة الأولى، بتأخير migration واحدة فقط.
> لذلك سلسلة النسب صريحة: `ACCEPTED_STATE_0` هو خط الأساس المُثبَت بـ16/16، وكل
> `ACCEPTED_STATE_N` لاحق يُلتقط عند نجاح النشر رقم N (§٦-ج) ويصبح **نقطة البداية
> الملزِمة** للـmigration التالية.

> **لماذا انتقل مقارن Step 5 إلى الخطوة ٢ لا ما بعد التطبيق.** مطالبة بـ16/16 *بعد*
> migration ناجحة شرط **يستحيل تحقيقه**: أي `CREATE TABLE` أو `ADD COLUMN` أو
> `CREATE INDEX` أو دالة أو سياسة جديدة تغيّر عمدًا بصمات columns أو indexes أو
> functions أو policies. صياغة تسمح بالتغيير ثم تشترط انعدامه تجعل كل migration حقيقية
> تفشل. المساواة التامة صالحة لإثبات **نقطة البداية**؛ وبعد التطبيق يصبح الفحص
> **expected-delta**: الفرق يساوي ما أعلنته الـmigration، ولا شيء غيره.

`db reset --linked` **مدمِّر** ويُستخدم على بيئة التحقّق وحدها. على الإنتاج: ممنوع (§٩).

### ما يجب أن يمرّ قبل الدمج

- `npm run test:security` — 4/4 بلا تخطٍّ. لأي migration تمسّ grants أو RLS أو
  `SECURITY DEFINER` أو predicates التفويض، فهو إلزامي دائمًا.

### ج · هدف `test:security` — يُثبَت آليًا، لا يُفترض

```text
قبل الدمج
  الهدف          بيئة التحقّق وحدها
  الهوية         تُثبَت آليًا قبل التشغيل
  ممنوع          أن يستهدف الإنتاج

بعد التطبيق
  الهدف          الإنتاج
  الوضع          قراءة فقط
  الهوية         تُثبَت آليًا قبل التشغيل
```

هذا البند مكتوب لأن Step 8 وقعت فيه فعلًا: نُسخ `.env.local` إلى بيئة الاختبار دون فحص
وجهته، فاتصلت البوابة بالإنتاج اتصالًا ثانيًا لم يأذن به الـrunbook. **هوية الهدف تُقاس،
لا تُورَّث من ملف بيئة.**
- `npm run test:migration-dir` — **تحديث allowlist الحارس في الـcommit نفسه** الذي يحمل
  الـmigration الجديدة، لا في commit لاحق. وجود نافذة يكون فيها الحارس أخضر وخاطئًا هو
  بالضبط ما يجب منعه.

## ٦. Preflight الإنتاج

### أ · قبل التطبيق — كلها إلزامية

```text
origin/master            == الـSHA المفوَّض بالضبط
working tree             نظيف — git status --porcelain فارغ
baseline                 956400 بايت · cf3de852…790d7
migration-directory guard        PASS
migration version uniqueness     PASS · لا تكرار
local migration set              LOCAL  — مرتَّبة بالـversion، مسجَّلة
remote migration set             REMOTE — مرتَّبة بالـversion، مسجَّلة
authorized pending               AUTH   — من التفويض

  assert  |AUTH| == 1                         migration واحدة معلَّقة بالضبط
  assert  REMOTE included in LOCAL            كل version بعيدة موجودة محليًا
  assert  REMOTE == LOCAL[0 .. |REMOTE|-1]    بادئة مرتَّبة بالضبط، لا تقاطعًا
  assert  LOCAL minus REMOTE == AUTH          المعلَّق هو المفوَّض حرفيًا، لا أكثر ولا أقل
  assert  لا version في REMOTE غائبة عن LOCAL

  applied-file byte immutability — لكل version في REMOTE:      §٦-ج
    assert  توجد مدخلة مسجَّلة لهذه الـversion  (خط الأساس عبر مدخلة الـbootstrap)
    assert  الملف المحلي موجود
    assert  اسم الملف مطابق للمسجَّل
    assert  SHA-256 == file_sha256 المسجَّل عند التطبيق

  manifest chain integrity:                                     §٦-ج
    assert  ACCEPTED_STATE الجارية محدَّدة وسلسلتها متصلة حتى الجذر
    assert  sha256(applied-migrations.json) == applied_manifest_sha256 المسجَّل فيها
    assert  ACCEPTED_STATE_CURRENT.version == آخر version في REMOTE
supabase db push --dry-run --linked
  → يسمّي بالضبط الـmigration الواحدة المفوَّضة، ولا شيء غيرها
target project ref               مطابق حرفيًا للـref المفوَّض
linked ref                       مؤكَّد صراحةً قبل أي أمر
PROD_PRE = التقاط بصمات الإنتاج + الثوابت الأمنية الدائمة، قبل أي كتابة

  assert  PROD_PRE == ACCEPTED_STATE_CURRENT.fingerprints

    الإنتاج يبدأ من الحالة التي خُتمت آخر مرة، لا من حالة تشبهها
    وهذا فحص **مبكر**؛ الإثبات الملزِم يُعاد داخل الحماية (§٦-أ-٢)
```

> **ولماذا لا يكفي إثبات الفرق وحده.** بلا هذا التثبيت، أي انحراف غير مسجَّل حدث على
> الإنتاج قبل التطبيق يظهر في `PROD_PRE` **وفي** `PROD_POST` معًا، فيختصر نفسه من الطرح
> ويمرّ:
>
> ```text
> ACCEPTED_STATE_N
>       ↓  drift غير مسجَّل على الإنتاج
> PROD_PRE = الحالة N + drift
>       ↓  الـmigration تعمل بشكل صحيح
> PROD_POST - PROD_PRE == expected delta      ✅ يمرّ
>       ↓
> ACCEPTED_STATE_N+1  ← والانحراف صار معتمَدًا رسميًا
> ```
>
> فيغسل الـworkflow انحرافًا قديمًا ويختمه بدل أن يكشفه. وهذا أخطر ما يكون بعد فشل جزئي
> لم يُضِف صفًا للسجل: مجموعة الـversions وسلسلة الـmanifest تبقيان سليمتين تمامًا،
> بينما المخطط الفعلي تغيّر. **السلسلة تصبح دليلًا على حالة الإنتاج نفسها، لا على تاريخ
> الملفات وحده، عند هذا الشرط تحديدًا.**

> **«بادئة مرتَّبة بالضبط» ليست «لا فرق ظاهر».** الشرط الأخير — ألا توجد version بعيدة
> غائبة محليًا — هو حرفيًا الشرط الذي كان مخروقًا وأنتج الأزمة كلها: 137 صفًا في الإنتاج
> بلا مقابل في المستودع. فحص يكتفي بأن «الأعداد تبدو متقاربة» كان سيمرّ عليه.

> **`--linked` قيمته الافتراضية `true` في CLI 2.78.1.** أي أن `supabase db push` المجرَّد
> يستهدف المشروع المرتبط. **لا يُعتمد على الافتراضي أبدًا**: يُكتب `--linked` صراحةً،
> ويُثبَت الـref المرتبط قبله بقياس، لا بافتراض.

### أ-٢ · الكاتب الواحد، وإعادة القراءة النهائية

كل ما سبق يُثبت حالة **لحظة القياس**. بين آخر فحص والأمر الفعلي تبقى نافذة يستطيع فيها
ناشر آخر أن يكتب في السجل — فيصبح لدينا نفس الـSHA ونفس المجموعة المحلية، بينما تاريخ
الإنتاج تغيّر بعد الإثبات.

**الثابت:**

```text
Only one production migration deployment may be in-flight at a time.
```

### بوابة التفعيل — تفشل مغلقة

الثابت أعلاه لا يسري بإعلانه. **لا يجوز لـStep 9 أن يعتبر الـworkflow مفعَّلًا** قبل أن
تتحقّق **جميع الشروط الإلزامية** التالية:

```text
Workflow activation MUST FAIL CLOSED unless ALL of the following exist,
are enabled, and have been mechanically verified.

  1  الآلية موجودة       deployment mutex أو protected environment
                          أو قناة نشر متسلسلة
  2  الآلية مفعَّلة       لا معطَّلة ولا في وضع تحذير
  3  الآلية مُثبَتة آليًا  أُثبت أنها تمنع تزامن أكثر من production deployment واحد
  4  مرساة الثقة قائمة    النموذج A أو B أعلاه، مُثبَتًا آليًا
  5  الجذر مزروع          مدخلة bootstrap + ACCEPTED_STATE_0 كاملة (§٦-ج)
```

غياب أي شرط إلزامي أعلاه = الـworkflow **غير مفعَّل**، ولا يُنفَّذ نشر إنتاجي تحته. الافتراضي
هو الرفض، لا القبول: آلية غير مُثبَتة تُعامَل كغير موجودة.

### مرساة الثقة — التاريخ الذي تستند إليه السلسلة

السلسلة كلها تنتهي إلى commits منشورة على `origin/master`. وهذا يحمي **بشرط ألا يستطيع
الطرف نفسه إعادة كتابة ذلك التاريخ**؛ وإلا فإعادة كتابته تُعيد التزوير ممكنًا بخطوة واحدة.

**لا يُعدّ الـworkflow مفعَّلًا** ما لم يتحقّق **أحد** النموذجين — واحد يكفي:

```text
A) فرع authoritative محميّ
   force push                 ممنوع
   حذف الفرع / إعادة كتابة التاريخ  ممنوع
   الإغلاق                    fast-forward فقط
   الـSHA                     مُتحقَّق منه من الخادم

أو

B) مرساة مستقلة غير قابلة للتعديل
   closure SHA محفوظ خارج تاريخ Git القابل لإعادة الكتابة
```

غياب الاثنين معًا ← الـworkflow **غير مفعَّل** (تفشل مغلقة كما في البوابة أدناه). ولا
يُقبل «الاتفاق على عدم إعادة الكتابة» بديلًا: المرساة تُثبَت آليًا أو لا تُعدّ موجودة.

### الحماية مُمسَكة بلا انقطاع حتى التنفيذ

القراءة النهائية تتم **داخل نفس حماية الـsingle-writer**، وتظل الحماية قائمة دون انقطاع
حتى يكتمل الأمر:

```text
acquire single-writer protection
    │
    ├─ HEAD == origin/master == الـSHA المفوَّض
    ├─ git status --porcelain فارغ        ← الآن، لا وقت الـpreflight
    │
    ├─ sha256(ملف الـmigration المفوَّضة) == Migration file SHA-256 المفوَّض
    ├─ sha256(بيان الـexpected-delta)     == Expected-delta SHA-256 المفوَّض
    ├─ R1 → sha256(الأداة التعويضية)      == المسجَّل في التفويض
    ├─ R2 → أدلة النسخة والاسترجاع والتفويض الخاص مُثبَتة
    │
    ├─ REMOTE_FINAL = إعادة قراءة مجموعة الـmigrations البعيدة
    ├─ assert  REMOTE_FINAL == REMOTE_AUTHORIZED
    ├─ assert  canonical_digest(REMOTE_FINAL) == Authorized remote digest
    ├─ assert  linked project ref لم يتغيّر
    ├─ assert  AUTH لم تتغيّر  و |AUTH| == 1
    │
    ├─ dry-run نهائي: supabase db push --dry-run --linked
    ├─ assert  خرجه مطابق حرفيًا للخرج المسجَّل في التفويض
    │
    ├─ PROD_PRE_FINAL = إعادة التقاط بصمات الإنتاج + الثوابت الأمنية
    ├─ assert  PROD_PRE_FINAL == ACCEPTED_STATE_CURRENT.fingerprints
    │
    ├─ supabase db push --linked        الأمر المفوَّض حرفيًا
    │
    ├─ post-apply verification          §٦-ب  — على أساس PROD_PRE_FINAL
    ├─ تسجيل مدخلة الملف المطبَّق        §٦-ج  — أولًا
    ├─ بناء ACCEPTED_STATE_N+1          §٦-ج  — بعد تجزئة الـmanifest
    │
    ├─ closure commit                   الملفان معًا
    ├─ fast-forward إلى origin/master
    └─ تحقّق من الخادم: origin/master == closure commit
    │
release protection
```

> **لماذا يُعاد كل شيء تحت الحماية.** القياس خارج القفل يصلح **إنذارًا مبكرًا** يوفّر
> جهدًا، ولا يصلح إثباتًا أخيرًا قبل الكتابة. بين إثبات الـpreflight واكتساب القفل تبقى
> نافذة يستطيع فيها نشرٌ آخر أن **يفشل جزئيًا بلا صف في السجل**: `REMOTE_FINAL` تبقى كما
> هي تمامًا، والـmanifest وسلسلتها سليمتان، بينما المخطط لم يعد `PROD_PRE`. لذلك تُعاد
> القياسات الحسّاسة داخل القفل، ويُبنى الفرق على `PROD_PRE_FINAL` لا على القياس المبكر.

> **ولماذا تُجزَّأ البايتات هنا تحديدًا.** `db push` يقرأ **ملف الـworktree**، لا ما يحمله
> `origin/master` نظريًا. فتطابق الـSHA للـcommit لا يمنع تعديلًا غير مُلتزَم بعد
> الـpreflight. التفويض لا يصبح ملزِمًا إلا حين يُقاس على **البايتات التي ستُنفَّذ فعلًا،
> والهدف الذي ستُنفَّذ عليه، والحالة التي ستنطلق منها** — في اللحظة الأخيرة، وتحت الحماية.

**الخروج من الحماية قبل `db push` يُعيد السباق نفسه** بصورة أضيق: الأسيرشن ساعتها تُثبت
لحظة، لا فترة. الحماية تغطي القياس والتنفيذ معًا أو لا تكون حماية.

> **والنشر لا ينتهي عند رمز خروج الأمر.** ينتهي عند **إغلاق دائم منشور**: postflight
> ناجح، حالة مقبولة ملتقَطة، وسجل الإغلاق مثبَّت على `origin/master` ومُتحقَّق منه من
> الخادم. الإفراج عن الحماية قبل ذلك يسمح لناشرٍ ثانٍ بالبدء بينما الأول لم يُثبِت بعد ما
> فعله — فتُقاس حالة النشر الأول على قاعدة غيّرها الثاني.

> **وإذا نجح النشر على قاعدة البيانات وفشل تثبيت الإغلاق في Git** — انقطاع، عطل جهاز،
> رفض من الخادم — فالحالة **UNSEALED**:
>
> ```text
> UNSEALED = الإنتاج تغيّر، ولا يوجد سجل إغلاق منشور يصفه
>
> → STOP
> → لا يُسمح بأي نشر لاحق إطلاقًا
> → العلاج: استعادة الإغلاق وتثبيته بتفويض مستقل، بعد قياس الحالة الفعلية
> ```
>
> ليست حالة يُكمَل منها؛ هي حالة تُغلَق أولًا. النشر التالي على قاعدة بلا سجل إغلاق يبني
> على أساس لا أحد يعرف ما هو.

أي تغيّر ← **التفويض باطل · STOP · صفر كتابة**. وهذا ما يُكمل الربط بين الـdry-run
والحالة التي سيعمل عليها `db push` فعلًا.

### ب · بعد التطبيق

```text
supabase migration list          local set == remote set
السجل ازداد بصف واحد بالضبط — هو الـversion المفوَّضة
الصف الجديد في schema_migrations يطابق اسم الملف في المستودع

PROD_POST - PROD_PRE_FINAL == authorized expected-delta manifest
  المطابقة حرفية على الإنتاج نفسه، لا «مقارنة الفئات المعنية»
  ويسبق إنشاء ACCEPTED_STATE_N+1 — لا يُلتقط قبل نجاحها

data-impact assertions          كل تأكيدات قسم أثر البيانات (§٣)
npm run test:security            حيثما كان إلزاميًا
```

> **التحقّق على بيئة التحقّق لا يُغني عن التحقّق على الإنتاج.** §٥ تُثبت الـexpected-delta
> حيث يجوز الخطأ؛ وهذه تُثبتها حيث لا يجوز. حالة مقبولة تُلتقط قبل إثبات الفرق على
> الإنتاج تُوثّق افتراضًا لا واقعًا، وتصبح نقطة بداية كاذبة لكل ما بعدها.

### ج · سجل النشر — الحالة المقبولة والبصمات المطبَّقة

يُبنى ويُثبَّت ويُنشَر **أثناء الحماية وقبل الإفراج** (§٦-أ-٢)؛ والنشر لا يُعدّ مغلقًا قبله.

```text
مدخلة الملف المطبَّق — تُضاف إلى supabase/applied-migrations.json
  version              الـversion كما دخلت السجل
  filename             اسم الملف حرفيًا
  file_sha256          بصمة الملف المطبَّق بالضبط
  authorized_git_sha   الـcommit المفوَّض

ACCEPTED_STATE_N+1 — ملف مستقلّ وغير قابل للتعديل
  المسار                     supabase/accepted-states/<version>.json
  version                    الـmigration التي أنتج نشرُها هذه الحالة
  predecessor_version        الحالة المقبولة التي تسبقها مباشرة
  predecessor_state_sha256   بصمة ملف الحالة السابقة بالضبط
  predecessor_closure_commit الـcommit الذي ثبّت الإغلاق السابق
  comparator_id              هوية المقارن/المواصفة التي أنتجت البصمات
  fingerprints               الفئات الست عشرة + الثوابت الأمنية بعد postflight PASS
  applied_manifest_sha256    بصمة applied-migrations.json بعد إضافة المدخلة أعلاه
```

> **لا يحتوي ملف الحالة بصمة الـcommit الذي يحمله.** تسجيل `closure_commit` الجاري داخل
> الملف الداخل في ذلك الـcommit **دائرية لا تُبنى**: الـSHA يعتمد على المحتوى، والمحتوى
> يعتمد على الـSHA. لذلك تُسجَّل **إغلاقة السابق** فقط، ويُثبَت الإغلاق الجاري من
> `origin/master` وتحقّق الخادم لا من داخل نفسه.

### ترتيب البناء — حتمي ولا يُعكَس

`ACCEPTED_STATE_N+1` تحمل بصمة الـmanifest **بعد** إضافة المدخلة، فلا يمكن بناؤها قبلها:

```text
postflight PASS
  → append مدخلة applied-migrations الجديدة
  → hash للـapplied-migrations.json النهائي
  → بناء ACCEPTED_STATE_N+1 بتلك البصمة
      + predecessor_state_sha256
      + predecessor_closure_commit
  → closure commit  (الملفان معًا)
  → fast-forward إلى origin/master
  → تحقّق من الخادم
  → release
```

الملفان خارج `supabase/migrations/` فلا تراهما الـCLI، وكلاهما **append-only**: لا تُعدَّل
مدخلة سابقة ولا يُحذَف ملف حالة.

### الحالة الجارية — كيف تُحدَّد، لا كيف تُفترض

```text
ACCEPTED_STATE الجارية = ملف الحالة الذي version = آخر migration مطبَّقة على الإنتاج

assert  سلسلة predecessor متصلة بلا فجوة من الجذر حتى الحالة الجارية
assert  الجذر = ACCEPTED_STATE_0 لخط الأساس، predecessor_version = null
assert  لكل حالة غير جذرية:
          sha256(ملف الحالة السابقة) == predecessor_state_sha256 المسجَّل فيها
          predecessor_closure_commit موجود في تاريخ origin/master
```

### لماذا لا تكفي الـmanifest وحدها — سلسلة تجزئة لا ملف يثق بنفسه

الفحص في Rev 2.4 كان **دائريًا**: يقارن ملف الـmigration بالـmanifest، والاثنان قابلان
للتعديل معًا. من يعدّل `X.sql` ويعدّل `file_sha256` المقابل يمرّ:

```text
تعديل X.sql  +  تعديل مدخلتها في applied-migrations.json
        ↓
الملف يطابق الـmanifest
        ↓
الفحص يمرّ — والمرجع نفسه هو ما جرى تزويره
```

لذلك الـmanifest **لا تُصدَّق بذاتها**. كل إغلاق يثبّت بصمتها داخل ملف الحالة، وملفات
الحالة مسلسلة بـ`predecessor_version`، والجذر هو خط الأساس. فيصبح preflight:

```text
assert  sha256(applied-migrations.json كما هي الآن، حتى مدخلة آخر migration مطبَّقة)
          == applied_manifest_sha256 المسجَّل في ACCEPTED_STATE الجارية

assert  كل مدخلة سابقة مطابقة بايت-ببايت لما أثبته آخر إغلاق مقبول
```

أي تعديل رجعي يكسر السلسلة عند أول حلقة، ولا يمكن إخفاؤه إلا بتزوير كل الحلقات
اللاحقة **وcommits الإغلاق التي تحملها** — وهو ما ينتقل بالمشكلة من «ملف قابل للتحرير»
إلى «تاريخ منشور قابل للتدقيق».

### تمهيد الجذر — bootstrap خط الأساس

السجل يبدأ فارغًا بينما الـremote يحمل `20260821105505` بالفعل، فأول preflight ستفشل على
version لا مدخلة لها. الجذر يُزرع في **Step 9 قبل التفعيل**، لا يُستنتج:

```text
مدخلة bootstrap لخط الأساس — تُكتب مرة واحدة وتُصبح immutable
  version              20260821105505
  filename             20260821105505_baseline.sql
  file_sha256          cf3de852cecc49d29e5d24c6bbb6afcebf8d65aeb994b684f5fc0a21f02790d7
  bytes                956400
  authorized_git_sha   الـcommit الذي أدخل الملف إلى المستودع

ACCEPTED_STATE_0 — بنفس المخطط الدائم، بلا استثناء
  version                    20260821105505
  predecessor_version        null
  predecessor_state_sha256   null
  predecessor_closure_commit null
  comparator_id              هوية مقارن Step 5 المسترجَع
  fingerprints               الفئات الست عشرة كما أثبتها ذلك المقارن
  applied_manifest_sha256    بصمة applied-migrations.json وهي تحمل
                             مدخلة الـbootstrap وحدها
```

> **الجذر يلتزم بالمخطط نفسه.** جذر ناقص الحقول يجعل أول deployment يفحص حالةً لا تحمل
> ما يفحصه — وهو العيب نفسه في صورة أولى بدل أن يكون في صورة متكرّرة.

**غياب الجذر = الـworkflow غير مفعَّل** (§٦-أ-٢). ولا يُقبل استنتاجه من الحالة الراهنة:
يُزرع بالقيم المجمَّدة أعلاه، ويُطابَق عليها.

### ولماذا هذا هو الحارس الحقيقي للثابت append-only

الثابت في §٤ كان **سياسة بلا فحص**. الـpreflight يثبت بصمة خط الأساس وحده، ويقارن
مجموعات الـversions — والـversion لا تحمل محتوى. فالسيناريو التالي يمرّ صامتًا:

```text
migration X طُبِّقت على الإنتاج
        ↓
أحدهم يعدّل X.sql لاحقًا مع إبقاء الاسم والـversion
        ↓
local versions == remote versions
        ↓
db push يرى X «مطبَّقة» فلا يفعل شيئًا
        ↓
تاريخ يبدو سليمًا، وبايتات SQL مختلفة
```

وهذا تكرار للمشكلة التي استُهلكت Phase 2 كلها في إزالتها. لذلك يُضاف إلى preflight (§٦-أ):

```text
for every version in REMOTE:
    الملف المحلي موجود
    اسم الملف مطابق حرفيًا للمسجَّل
    SHA-256 للملف == file_sha256 المسجَّل عند التطبيق

اختلاف بايت واحد ← STOP
```

الحماية تنتقل من «الأسماء تتطابق» إلى **«البايتات تتطابق»**، وهو الفرق بين سجل يصف
التاريخ وسجل يدّعيه.

## ٧. STOP و rollback

يُفصَل فصلًا حادًّا بين **إرجاع نشر** و**إصلاح سجل**:

> **ممنوع كسياسة عامة:** `migration failed → migration repair --status reverted`.
> `repair` يغيّر **تمثيل** السجل ولا يطبّق SQL ولا يرجعه. استخدامه كردّ فعل على فشل يُخفي
> أثرًا موجودًا في قاعدة البيانات ويجعل السجل يكذب عنها.

`migration repair` أداة **break-glass للمصالحة فقط**، بتفويض مستقل مسمّى، لا جزء من أي
مسار نشر.

```text
قبل الإنتاج
  أي عدم تطابق            STOP · صفر كتابة على الإنتاج

أثناء التطبيق أو بعده
  أي فشل                  الإجراء المُلزِم أدناه، بالترتيب
```

### الفشل بعد تطبيق جزئي أو مُثبَّت — إجراء مُلزِم

تحت هذا الـADR لا يكون معلَّقًا سوى migration واحدة (§٣)، لكنها **قد تحمل عدة عبارات**،
وليست كل العبارات transactional بالسواء. الفشل في المنتصف يترك حالة لا يصفها لا التفويض
ولا السجل. الترتيب التالي ليس اقتراحًا:

```text
١  STOP فورًا. لا أمر إضافي. لا repair. لا إعادة محاولة.

٢  PRESERVE — التقط، قبل أي شيء آخر:
     schema_migrations كاملًا
     خرج الأمر الفاشل حرفيًا
     البصمات البنيوية والأمنية كما هي الآن

٣  CLASSIFY الحالة الفعلية لقاعدة البيانات — لا الحالة المقصودة:
     أي migrations طُبِّقت كاملة
     أيها طُبِّقت جزئيًا (على مستوى العبارة)
     أيها لم تُطبَّق إطلاقًا
   ويُحدَّد ذلك بفحص الكائنات نفسها، لا بقراءة السجل.

٤  عندئذٍ فقط يُختار العلاج:
     migration تعويضية مصمَّمة ومراجَعة ومفوَّضة بذاتها
     أو مسار recovery مُعتمَد مسبقًا (R1/R2)
```

> **السجل يقول ما سُجِّل؛ المخطط يقول ما هو موجود.** بعد فشل جزئي قد يتناقضان، والسجل
> ساعتها **مصدر خاطئ** لقرار التعافي. لهذا الخطوة ٣ تفحص الكائنات لا الصفوف.

**ممنوع في كل الأحوال:** إصلاح السجل ليطابق النية.

> **ما لا يقيسه هذا التصنيف.**
>
> ```text
> R0/R1/R2 classify rollback/data-loss characteristics only.
> They are NOT an overall operational-risk rating.
> ```
>
> الأثر التشغيلي — الأقفال، مدة التنفيذ، حجم الجدول، الـDDL الحاجب، أثر التزامن، والزمن
> المتوقَّع للتنفيذ — يُقاس **مستقلًّا** ضمن production preflight وفحوص المخاطر التشغيلية
> في Step 9، ولا يُشتقّ من الصنف.
>
> وتبعًا لذلك: **R2 ليست «أخطر migration على الإطلاق»**، بل أعلى صنف من حيث الإرجاع وفقد
> البيانات فقط. migration مصنَّفة **R0** قد تحتاج تفويضًا تشغيليًا خاصًا لو كانت ستأخذ
> قفلًا ثقيلًا على جدول ضخم — والتصنيف وحده لن يكشف ذلك.

### تصنيف الـrollback — يُحدَّد **قبل** التنفيذ، وبقاعدة لا بتقدير

ليس كل DDL قابلًا للإرجاع بالمعنى نفسه. والتصنيف **لا يُترك لتقدير المشغّل وقت التنفيذ**؛
يُشتقّ من العمليات الموجودة في الملف عبر الجدول التالي:

```text
R0  إنشاء/إضافة فقط — دون تغيير دلالة أو صلاحيات كائن قائم
    CREATE TABLE            جدول جديد
    CREATE INDEX            فهرس جديد   (عدا CONCURRENTLY — انظر أدناه)
    ADD COLUMN              nullable، بلا DEFAULT يغيّر سلوك قائمًا
    CREATE FUNCTION | VIEW | TRIGGER | POLICY   كائن جديد فعلًا لا بديل لقائم
    INSERT صفوف مرجعية/seed لا تُغيّر صفوفًا قائمة

R1  يغيّر الشكل أو الدلالة أو الصلاحيات — الإرجاع بـmigration تعويضية مكتوبة
    CREATE OR REPLACE  على كائن **قائم**   ← استبدال دلالة، لا إنشاء
    GRANT | REVOKE                          ← تغيير صلاحيات، وREVOKE ليست إضافية أصلًا
    ADD CONSTRAINT ... NOT VALID            ← لا يفحص الصفوف القديمة لكنه يغيّر قبول
                                               الكتابات الجديدة
    RENAME  جدول أو عمود
    ALTER COLUMN TYPE  توسيعي بلا فقد
    ADD CONSTRAINT  مع تحقّق
    SET NOT NULL
    UPDATE للتعبئة الرجعية (backfill)
    DROP  POLICY | TRIGGER | INDEX
    تغيير جسم دالة SECURITY DEFINER أو search_path لها

R2  مدمِّر أو مُفقِد للمعلومة
    DROP TABLE | DROP COLUMN
    ALTER COLUMN TYPE  تضييقي أو بتحويل فاقد
    DELETE | TRUNCATE
    DROP FUNCTION  تعتمد عليها سياسة أو دالة أخرى
    أي شيء يمسّ auth.* أو سطح خط الأساس الأمني في ADR 0004
```

أربع قواعد تجعلان الاشتقاق حتميًا:

1. **migration تحتوي عمليات من أصناف مختلطة تأخذ الصنف الأعلى.**
2. **أي عملية غير مذكورة أعلاه = R2** حتى يُعاد تصنيفها صراحةً في المراجعة **بشخص ثانٍ**.
   الافتراضي عند الغموض هو الأشدّ، لا الأسهل — ولا يجوز للمشغّل تخفيض التصنيف وحده.
3. **الفارق بين R0 وR1 هو وجود كائن قائم، لا صيغة الأمر.** `CREATE OR REPLACE` على كائن
   جديد فعلًا = R0؛ على كائن قائم = R1 على الأقل. من لا يستطيع إثبات أن الكائن جديد
   يعامله كقائم.
4. **أي عملية تمسّ الصلاحيات أو المصادقة أو سطح خط الأساس الأمني** تخضع لقاعدة ADR 0004
   أيضًا، ويؤخذ **الأشدّ** من التصنيفين.

> **`CREATE INDEX CONCURRENTLY` حالة خاصة، ولا يُوضَع في R0.** خصائصه المعاملاتية مختلفة:
> لا يعمل داخل transaction block، وقد يترك فهرسًا `INVALID` عند الفشل يحتاج تنظيفًا
> صريحًا. تُحدَّد معالجته — والتحقّق منه بعد التطبيق — في **Step 9**، ولا يُعامَل كأنه
> DDL مطابق لبقية الفئة.

| الصنف | ما يلزم |
|---|---|
| **R0** | المسار القياسي |
| **R1** | تُكتب الـmigration التعويضية **وتُراجَع قبل** التطبيق، وتُذكر في التفويض — **وتُحفَظ خارج دليل الـmigrations** (انظر أدناه) |
| **R2** | نسخة احتياطية مثبَتة ومُتحقَّق منها + تفويض خاص منفصل + فصل أدوار كامل (§٢) |

التصنيف حقل إلزامي في التفويض (§٣). migration بلا تصنيف = بلا تفويض.

### أين تعيش الـmigration التعويضية لـR1

كتابتها داخل `supabase/migrations/` **يجعلها migration ثانية معلَّقة**، فتنكسر
`|AUTH| = 1` وتُوقِف الـpreflight نفسها. الموضع محدَّد:

```text
R1 recovery artifact
  المسار        supabase/recovery/<version>_compensating.sql
  الرؤية        خارج supabase/migrations/ — غير مرئية للـCLI
  الحالة        immutable بعد المراجعة
  التسجيل       المسار + SHA-256 في التفويض (§٣)

**لا تنتقل هذه الأداة إلى دليل الـmigrations أبدًا كما هي.**
نقلها بحالها يُنتج version مكرَّرة مرئية للـCLI — وهو ما تمنعه §٤ صراحةً،
لأن الـversion الأصلية مسجَّلة بالفعل في السجل.

عند الحاجة إليها فعلًا:
  تُستخدم **مصدرًا** لتأليف migration جديدة
  بـ<14-digit> جديد واسم ملف جديد
  وتدخل الدورة كاملة ومستقلة: |AUTH| = 1، preflight، تفويض مسمّى، postflight
```

أي أن وجودها **جاهزية**، لا نشر معلَّق.

## ٨. الممنوع صراحةً على الإنتاج

```text
migration repair             ⛔ ليس آلية نشر — break-glass بتفويض مستقل فقط
SQL Editor                   ⛔ لنشر تغييرات المخطط
Dashboard / Table Editor     ⛔ لنشر تغييرات المخطط
تنفيذ SQL يدوي               ⛔ كمسار migration اعتيادي
db push --include-seed       ⛔ على الإنتاج
db push --include-all        ⛔ على الإنتاج — «كل ما ليس في سجل الـremote» تعريف يبتلع
                                المجهول؛ المفوَّض يُطبَّق لأنه مفوَّض، لا لأنه ناقص
db push --include-roles      ⛔ بلا تفويض منفصل يذكره صراحةً
db push بلا --linked صريح    ⛔ الافتراضي true يخفي الهدف
migration down               ⛔ على الإنتاج
db reset --linked            ⛔ على الإنتاج — مدمِّر
migration squash             ⛔ يعيد كتابة التاريخ — بتفويض مستقل فقط
npm run test:all             ⛔ على الإنتاج — يكتب في الـledger (ADR 0004)
```

## ٩. ما لا يُمَسّ

- **تجميد خط الأساس الأمني في ADR 0004 §١–§٥** — حارس دائم ومنفصل تمامًا. هذا الـADR لا
  يمسّه، وقصر حظر `db push` لا يُقرأ بأي حال كتخفيف له.
- **أدلة الاسترجاع لصفوف الـ143** — تُحفَظ، لا تُحذَف، ولا يُعاد توليدها. هي النسخة الوحيدة
  من SQL كما طُبِّق فعلًا؛ الأرشيف في Git ليس مكافئًا لها.
- **scratch-3 و scratch-4** — يُحفظان.
- **الفروع المحلية غير المنشورة** — ليست مراجع migration authoritative، ولا تدخل أي قرار
  migration إلا عبر workflow منفصل مفوَّض.

## البدائل المرفوضة

| البديل | سبب الرفض |
|---|---|
| رفع الحظر لأن الشرط تحقّق | تحقُّق الشرط يُنهي المبرِّر ولا يُنشئ ضوابط بديلة. الرفع بلا بديل يعيد الحالة التي أنتجت الانحراف. |
| إبقاء الحظر الشامل إلى الأبد | يجعل خط الأساس نهاية التاريخ لا بدايته، ويدفع التغييرات إلى مسارات غير مسجَّلة — وهو المصدر الأصلي للانحراف. |
| اختراع آلية نشر خاصة بدل `db push` | يضع أداتنا موضع ادّعاء التكافؤ مع أداة المورِّد بلا إثبات. `db push` يقارن الملفات بالسجل ويطبّق غير المطبَّق — وهو بالضبط المطلوب. المشكلة كانت في التاريخ لا في الأداة. |
| `db push` مباشرة بعد اختبار محلي | البيئة المحلية ليست الإنتاج. Step 5 أثبت التكافؤ على مشروع أُنشئ من خط الأساس، لا على جهاز مطوِّر. |
| مشروع scratch جديد مدفوع لكل migration | التكلفة بلا مقابل. المطلوب بيئة قابلة للمسح وإعادة البناء من خط الأساس، لا بيئة جديدة. |
| `repair --status reverted` كعلاج للفشل | يصلح تمثيل السجل لا أثر قاعدة البيانات، فيجعل السجل يكذب عن الحالة الفعلية. |


**التوقيع تمّ — ومع ذلك `supabase db push` على الإنتاج ما زال ممنوعًا بموجب ADR 0004.**
الشرطان اللذان يرفعانه معًا مذكوران أدناه، ولا يكفي أحدهما.

### بعد التوقيع

توقيع هذا الـADR **لا ينفّذ نفسه**. تفعيل الـworkflow ميكانيكيًا — الحُرّاس، فحوص الهوية،
البوابات — عمل منفصل (Step 9) يحتاج تفويضه الخاص، **وممنوع خلاله تطبيق أي migration على
الإنتاج أثناء تصميم الـworkflow واختباره**.

```text
Signing ADR 0005 does NOT authorize production db push.

ADR 0004's production-write prohibition remains in force until:
  1  Step 9 has passed its fail-closed activation gate   (§٦-أ-٢)
  2  a separate named migration authorization exists      (§٣)

Both. Neither alone lifts it.
```

لا يُقرأ التوقيع بأي حال كإذن. هو يُنشئ **القواعد** التي سيُنفَّذ تحتها النشر لاحقًا، ولا
يُنشئ إذنًا بنشرٍ بعينه — والإذن لا يوجد إلا في تفويض مسمّى بعد تفعيل مُثبَت.
